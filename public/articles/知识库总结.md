# 知识库学习总结

## 一、上传文档接口链路

上传文档接口的核心职责是：**把文件安全放进系统，并生成文档主表记录，不做分块和向量化**。

主要链路：

1. **先过上传限流 Filter**：如果是上传请求，就通过 Redisson 的 `RPermitExpirableSemaphore` 抢上传许可；抢不到直接返回 429，抢到才继续。这样做是为了在 multipart 解析之前挡住过多并发，避免临时文件、磁盘 IO、对象存储写入同时被打满。
2. **本地文件上传**：Spring/Tomcat 先按 `max-file-size` 和 `max-request-size` 做大小限制，Controller 拿到 `MultipartFile` 后，Service 校验知识库、来源类型、处理模式和分块参数，再上传到 S3/RustFS。这样分层是为了让容器负责通用上传安全，业务层只关注文档是否合法。
3. **URL 文件上传**：Service 先用 `HEAD` 探测远程文件大小、类型、文件名；如果 HEAD 不可靠，就 GET 流式下载，边读边限制大小，先落本地临时文件，再上传对象存储。这样做是因为远程源站的 `Content-Length` 可能不准，先落临时文件可以拿到真实大小，也避免把远程文件整包读进内存。
4. **写文档主表**：拿到对象存储返回的文件 URL、文件名、大小、类型后，插入知识库文档表，状态通常是 `PENDING`，`chunkCount = 0`。这样做是为了把“文件已进入系统”和“文件已完成分块”区分开，后续再通过开始分块接口进入加工阶段。
5. **限流位置选择**：单体项目放在 Filter 层，微服务更适合放在 Gateway 层。原因是限流越靠前，越能保护后端线程、multipart 解析、临时文件和磁盘 IO；业务服务内部 Filter 可以作为兜底。

一句话总结：**Filter 管上传并发，Spring/Tomcat 管文件大小，Service 管业务校验、对象存储和文档表落库。**

## 二、分块接口链路

开始分块接口的核心职责是：**安全启动异步分块任务，不在请求线程里真正解析、分块和向量化**。

主要链路：

1. **请求线程只启动任务**：进入 `startChunk(docId)` 后，构造分块事件并发送 RocketMQ 事务消息，消息先是半消息。这样做是为了让用户请求快速返回，把文件解析、分块、embedding 这些耗时操作移到异步 Consumer 中。
2. **本地事务抢运行权**：RocketMQ 本地事务里通过 CAS 把文档状态改成 `RUNNING`。这样做是为了防止同一文档被重复启动分块，同时保证“文档进入 RUNNING”和“消息最终可消费”绑定在一起，避免状态改了但没人处理。
3. **同步 schedule 配置**：本地事务里会调用 `scheduleService.upsertSchedule(documentDO)`，为 URL 来源文档维护定时同步配置。这样做是因为 URL 文档后续可能需要自动刷新，开始分块时顺手把未来的调度信息准备好。
4. **Consumer 异步处理**：本地事务成功后消息提交，Consumer 插入分块日志，再根据 `processMode` 选择普通 chunk 模式或 pipeline 模式。插入日志是为了记录本次执行的模式、耗时、结果和错误，便于审计和排障。
5. **普通模式和 Pipeline 模式**：普通模式走“对象存储读文件 -> Tika 提取文本 -> 分块策略切分 -> embedding”；Pipeline 模式交给 `ingestionEngine.execute(...)` 按节点编排处理。这样拆分是为了同时支持简单固定流程和可配置 ETL 流程。
6. **统一持久化和收尾**：拿到 `VectorChunk` 后，用编程式事务删除旧 chunk、插入新 chunk、删除旧向量、写入新向量，并更新文档状态。这样做是为了避免新旧 chunk 或向量混在一起，也避免把文件解析、embedding 这种耗时操作放进长事务。

一句话总结：**事务消息保证“文档进入 RUNNING”和“消息可消费”一致，Consumer 负责真正分块，编程式事务负责新旧 chunk 和向量的原子切换。**

## 三、定时同步链路

定时同步的核心职责是：**后台定期检查 URL 文档是否变化，变化后自动刷新文件、重新分块和重建向量**。

主要链路：

1. **schedule 配置来源**：上传或开始分块 URL 文档时，会写入或更新 schedule 主表，保存 `docId`、`kbId`、`cronExpr`、`enabled`、`nextRunTime`。这样做是为了把用户配置的 cron 转成系统可扫描、可锁定、可恢复的任务记录。
2. **统一扫描器触发**：Spring `@Scheduled` 统一扫描 schedule 表，而不是给每个文档创建一个 Java 定时任务。这样做更适合动态任务，因为文档可以随时增删改，统一扫描表比动态注册大量定时器更稳定、可控。
3. **第一层并发控制**：调度器通过 `lockUntil` 抢 schedule 级数据库租约锁，谁更新成功谁获得调度资格。这样做是为了在多实例部署时，避免多个节点同时调度同一条 schedule；心跳续租则是为了防止长任务执行中锁提前过期。
4. **变更检测**：优先用 `HEAD` 的 `ETag` 和 `Last-Modified` 判断是否变化；不可靠时再 GET 下载并计算内容 hash。这样做是为了尽量避免无意义的下载、分块和向量化，降低对象存储、模型调用和向量库写入成本。
5. **第二层并发控制**：确认文件变化后，还要通过文档表 `RUNNING` CAS 抢文档运行权。这样做是为了防止定时刷新和手动分块同时处理同一份文档，schedule 锁只能防重复调度，不能覆盖所有文档入口。
6. **刷新执行**：抢到运行权后，上传新文件到对象存储，调用分块链路重建 chunk 和向量，并更新 schedule 的下一次执行时间和远程文件标识。这样做是为了让文档、chunk、向量和调度状态最终一起收敛到新版本。

一句话总结：**schedule 的 `lockUntil` 防重复调度，document 的 `RUNNING` CAS 防同一文档重复执行，变更检测决定是否真的需要重新分块。**

## 四、文档启用/禁用接口链路

文档启用/禁用接口的核心职责是：**控制整份文档是否参与检索，不是删除文档，也不是重新分块**。

主要链路：

1. **前置校验**：先查文档是否存在，`RUNNING` 状态禁止修改，目标状态相同直接返回。这样做是为了避免一边分块或刷新，一边改变检索可见性，也避免重复操作浪费向量写入成本。
2. **禁用文档**：在编程式事务里把文档 `enabled` 改成 `0`，同步 schedule，把所有 Chunk 的 `enabled` 改成 `0`，并删除该文档全部向量。这样做是为了保留数据和历史，但让检索不再召回这份文档。
3. **启用文档**：先在事务外读取 Chunk 并重新计算 embedding，再在事务内恢复文档和 Chunk 的 `enabled`，同步 schedule，并写回向量。这样做是因为禁用时向量已经删除，启用必须重建向量；embedding 放事务外可以避免长事务。
4. **enabled 和 deleted 区别**：`enabled` 表示是否参与检索，`deleted` 表示记录是否删除。这样区分后，禁用可以做到“临时下线”，删除才是真正的数据清理。

一句话总结：**禁用是保留数据但下线检索能力，启用是恢复检索能力并重建向量。**

## 五、文档与 Chunk 管理接口链路

文档管理接口管整份文档，Chunk 管理接口管局部知识片段，二者不要混。

主要链路：

1. **文档删除**：校验文档存在且不是 `RUNNING`，然后删除 Chunk、schedule、分块日志、文档记录、向量和对象存储文件。这样做是为了按整份文档维度清理干净，避免数据库、向量库、对象存储出现孤儿数据。
2. **文档更新**：可修改文档名、处理模式、分块策略、pipeline 配置和 URL 定时配置；如果 schedule 字段变化，会同步 schedule 表。这样做是为了允许用户调整后续处理策略，但不自动重分块，避免一次普通配置修改触发高成本重建。
3. **Chunk 新增**：校验文档可编辑后，插入新 Chunk，更新 `chunk_count`，并生成 embedding 写入向量库。这样做是为了支持人工补充知识片段，不必重跑整篇文档。
4. **Chunk 更新**：原地更新当前 Chunk 内容，重算 hash、字符数、token 数，并 upsert 当前 Chunk 向量。这样做是为了支持局部修正；它不是删旧插新，不会影响其他 Chunk，也不会改变 chunk 数量。
5. **Chunk 删除/启停**：删除 Chunk 会删除对应向量；启用 Chunk 会重建向量，禁用 Chunk 会删除向量。这样做是为了让 Chunk 表状态和向量库检索能力保持一致。
6. **和重新分块的区别**：管理接口是局部维护，整篇文档重新分块或定时刷新才会按 docId 删除所有旧 Chunk 和旧向量再批量写入新结果。这样区分可以避免小改动触发大成本重建。

一句话总结：**文档接口管整体生命周期，Chunk 接口管局部精修；单条 Chunk 更新不是删旧插新，整篇重分块才是删旧插新。**

## 六、知识库文件上传大小限制原理

### 1. 这篇文章主要回答的是什么问题

这篇文章主要回答的是一个非常常见、但又很容易误解的问题：

**Spring Boot 配了上传大小限制之后，如果用户上传一个远超限制的大文件，服务器会不会先把整个文件读进内存，再发现超限，最后导致 OOM？**

文章给出的核心结论是：

**不会。**

Spring Boot 配合 Servlet 容器（这里主要是 Tomcat）时，针对上传大小限制有比较完整的“早期拒绝 + 流式处理 + 临时文件”机制，不会把一个超限的大文件先整体塞进 JVM 内存再处理。

### 2. 为什么很多人会误以为“先读后检查”

这个误解其实很自然，因为很多人对上传流程的直觉是：

1. 先把文件读进来
2. 再判断大小是否超限
3. 最后决定保存还是报错

这个直觉在小文件场景下不容易暴露问题，但一旦把文件放大到几百 MB 甚至 1GB，就会让人担心：

- 如果先完整读入内存，再做校验，就可能直接把服务内存打爆
- 如果多个超大上传并发过来，风险会进一步放大

而这篇文章的价值就在于，它把这个“直觉流程”和真实实现区分开了。

### 3. 真正的底层机制是什么

这篇文章总结下来，其实是三层机制一起生效：

#### 3.1 HTTP 协议层：先看 `Content-Length`

上传请求一般会带上 `Content-Length` 请求头。

它的作用很关键，因为服务器在**还没有真正读取请求体内容之前**，就已经知道这次请求大概有多大了。

所以从原理上说，服务端并不一定要“先把文件收下来再判断大小”，它完全可以：

- 先看请求头
- 发现这次请求已经超出允许范围
- 直接拒绝

这就是所谓的“早期拒绝”基础。

#### 3.2 Tomcat 层：优先做请求级拦截

Tomcat 在处理请求时，会先解析请求头。

如果请求头里声明的体积明显超出可接受范围，那么它可以直接拒绝请求，而不是继续把整个请求体读进来。

文章里重点提到了这几个点：

- Tomcat 能在比较早的阶段拿到 `Content-Length`
- 超限时可以直接中止处理
- 正常情况下也不是整包读入内存，而是按流式方式处理

也就是说，**Tomcat 本身就是第一道防线**。

#### 3.3 Spring Boot / Spring MVC 层：multipart 解析时边读边检查

真正进入 Spring MVC 的 multipart 解析后，也不是把整个文件一次性装进内存。

文章结合 `StandardServletMultipartResolver` 和 `request.getParts()` 的流程解释了这一点：

- Spring MVC 触发 multipart 解析
- 底层调用 Servlet 的 `getParts()`
- Tomcat 在解析 `Part` 时边读边处理
- 一旦发现超限，就直接抛出异常

所以即使是“单个文件超限”的场景，也不是先把整个文件都读到 JVM 堆里，再抛 `MaxUploadSizeExceededException`。

### 4. 为什么不会把超大文件整包读进内存

这篇文章最值得记住的一点是：

**上传处理依赖的是流式机制，而不是把整个文件作为一个大字节数组塞进内存。**

正常流程更接近这样：

1. Tomcat 读取一小块数据
2. 先放进一个很小的缓冲区
3. 超过阈值后就写入临时文件
4. 后续继续边读边写
5. Controller 层最后拿到的是 `MultipartFile` 包装对象

这意味着：

- 内存里常驻的是小缓冲区，不是完整文件
- 大文件的主体内容通常落在临时文件里
- `MultipartFile` 本身并不等于“整个文件已在内存中”

### 5. `MultipartFile` 到底是什么

这篇文章专门纠正了一个很容易混淆的点：

**Controller 拿到 `MultipartFile`，不代表文件内容已经完整在内存里。**

更准确地说：

- `MultipartFile` 更像是一个包装器
- 它底层通常关联的是临时文件或 Part 对象
- 真正会不会把整个文件读进内存，取决于你后续怎么使用它

例如：

- `file.getBytes()`：可能把整个文件读进内存
- `file.getInputStream()`：更偏流式读取
- `file.transferTo(...)`：更适合直接转存文件

所以文章实际上也在提醒我们：

**框架层不等于一定高内存，占不占内存，很多时候取决于业务代码怎么消费这个上传文件。**

### 6. 这几个配置分别控制什么

这篇文章把上传大小限制相关的几个配置区分得比较清楚。

#### 6.1 `max-file-size`

表示单个文件的最大允许大小。

如果一个文件本身就超过这个值，就会触发单文件超限。

#### 6.2 `max-request-size`

表示整个请求的最大允许大小。

它不只是看某一个文件，而是看整次 multipart 请求的总大小，包括：

- 多个文件
- 普通表单字段
- multipart 协议本身的额外开销

#### 6.3 `file-size-threshold`

表示多大以上的数据开始写临时文件。

文章强调：

- 默认值为 `0`
- 这意味着几乎所有上传内容都会直接走临时文件，而不是先囤在内存里

这个默认值其实很适合生产环境，因为它的目标就是：

**尽量用磁盘临时文件换掉大块内存占用。**

### 7. 超限时为什么你看到的是业务 JSON，而不是 413

文章还讲了一个很贴近实战的问题：

明明底层是上传超限，为什么前端看到的却是统一 JSON 错误结构，甚至 HTTP 状态码看起来还是 `200`？

这是因为项目里做了全局异常拦截。

也就是说：

- 底层先抛出上传超限相关异常
- 全局异常处理器把它捕获
- 再包装成统一返回结构

所以你在接口层看到的是：

- 一个业务化的错误码
- 一个更友好的错误提示

而不是直接把容器原始报错暴露出去。

这点很重要，因为它说明：

**“返回格式长什么样”是业务层包装结果，不等于“底层是否真的做了早期拒绝”。**

### 8. 如果客户端不老实，会不会绕过限制

文章还讨论了两个很有代表性的边界场景。

#### 8.1 不发 `Content-Length`

如果客户端不带 `Content-Length`，而是走分块传输，容器也不是完全失去控制。

这时底层仍然可以采用“边读边累计”的方式，只要累计大小超过限制，就会立即停止。

#### 8.2 伪造 `Content-Length`

如果客户端声明自己只传 10MB，结果实际上持续发更多数据，容器也会在实际读取过程中发现异常，并中断连接。

所以上传限制并不是只靠客户端诚实上报大小，而是：

- 请求头做第一层判断
- 实际读取过程继续做第二层校验

### 9. 这篇文章和“30MB 文件为什么占了 100MB 内存”有什么区别

这两篇文章很容易混，但它们在回答的是两个不同问题。

这篇“文件上传大小限制原理”主要在讲：

- 超限文件为什么不会先把 JVM 堆撑爆
- Spring Boot / Tomcat 为什么具备早期拒绝能力
- 正常上传为什么主要依赖流式处理和临时文件

而前面那篇“30MB 文件为什么占了 100MB 内存”主要在讲：

- 某些上传链路里，为什么在业务处理阶段仍然可能出现明显内存放大
- 这种放大往往来自 SDK、签名、缓冲、重复拷贝、对象构建等额外环节

所以不能把两篇文章理解成互相矛盾。

更准确的理解是：

- **框架底层不会傻到先把超限文件整包读进 JVM 再拒绝**
- **但业务链路如果自己做了多次缓冲、转换和对象复制，依然可能出现高内存占用**

### 10. 这部分最值得记住的点

1. 上传大小限制不是“文件全进内存后再判断”，而是有早期拒绝机制。
2. `Content-Length` 是服务端提前判断请求体大小的重要依据。
3. Tomcat 是第一道防线，Spring MVC 的 multipart 解析是第二道防线。
4. 正常上传也不是整包进内存，而是流式读取 + 临时文件落盘。
5. `MultipartFile` 不等于“文件内容已经完整在内存中”。
6. 真正容易把文件整包读进内存的，很多时候是业务代码里的 `getBytes()` 这类操作。
7. `max-file-size` 控制单文件，`max-request-size` 控制整次请求，`file-size-threshold` 控制何时落临时文件。
8. 即使有大小限制，也仍然需要并发控制，因为大量合法上传一样会制造临时文件和 IO 压力。

### 11. 一段适合回头快速看的总结

“知识库文件上传大小限制原理”这篇文章，本质上是在帮我们纠正一个错误直觉：Spring Boot 并不会先把超限的大文件完整读进内存再拒绝。真实机制是，Tomcat 会先利用请求头信息尽早做一轮判断，进入 multipart 解析后也会继续边读边检查；而正常上传则主要依赖流式读取和临时文件来承接大文件内容，所以 JVM 内存里通常只保留小缓冲区，而不是整份文件。需要特别注意的是，这只能说明框架底层已经尽量避免“超限即 OOM”，并不代表业务代码天然不会高内存；如果后续处理里自己做了整包读取、重复拷贝或 SDK 多层缓冲，内存仍然可能被放大。因此正确理解应该是：**大小限制解决的是单请求超限防护，流式处理解决的是框架层内存安全，而并发限流和业务代码优化解决的是上传链路整体资源稳定性。**

## 七、为什么上传30MB文件占了100MB内存？

### 1. 这个问题的本质是什么

表面看，上传一个 30MB 文件，直觉上最多占 30MB 左右内存。

但实际工程里，经常会看到明显更高的堆占用，比如 30MB 文件触发 80MB、100MB 甚至更高的瞬时内存波动。

这说明问题不在“文件本身有多大”，而在于：

- 上传链路中有没有发生多次内存拷贝
- SDK 或中间件是不是把文件内容提前读进内存
- 看起来像“流式”的 API，底层是不是真的流式

这篇补充最值得记住的一点就是：

**不要只看我们自己写的代码是否流式，还要看底层 SDK 的真实行为。**

### 2. 为什么会出现内存放大

上传内存放大，通常不是单一原因，而是多段链路叠加的结果。

在这篇文章的分析里，核心矛头指向的是对象存储 SDK 的上传实现，尤其是：

- `fromFile()`
- `AsyncRequestBody`
- payload signing

也就是说，问题不一定出在 Spring MVC 的 `MultipartFile` 本身，而可能出在：

**文件已经落到临时文件后，继续往对象存储上传的那一段。**

### 3. “看起来流式”为什么不一定真流式

这篇文章反复强调一个非常重要的工程认知：

很多 API 的名字会让人误以为它是流式的，比如：

- `RequestBody.fromFile(...)`
- `AsyncRequestBody`

但在某些 SDK 实现下，为了完成签名、校验、重试、内容长度计算等处理，底层可能仍然会：

- 预读文件内容
- 做额外字节数组拷贝
- 在内存里构造完整请求体

于是你在业务代码里虽然没有写 `readAllBytes()`，但底层已经替你做了类似的事情。

所以“看起来是流式”不等于“真实零拷贝”。

### 4. 这篇文章指出的关键根因

结合文档内容，这次内存放大的核心根因可以概括成一句话：

**对象存储 SDK 的签名上传链路，把原本应该基于文件流传输的数据，变成了带额外缓冲和拷贝的内存处理过程。**

文章里尤其提到：

- payload signing 会影响上传行为
- AWS Java SDK 某些上传路径并没有按直觉那样流式工作
- 异步 API 也不代表不会产生大块内存占用

所以问题的根源不是“30MB 文件太大”，而是：

**上传实现路径选错了。**

### 5. 为什么这类问题平时不容易被发现

这篇文章还提了一个很真实的点：这类问题在很多团队里其实长期存在，只是通常不容易暴露。

原因大致有四类：

1. 文件不够大，内存波动不明显。
2. JVM 堆很大，偶发峰值被吞掉了。
3. 上传不是热点路径，监控上只是一瞬间毛刺。
4. 大家默认相信 SDK 的“fromFile/async”就是流式实现，不会特意去验证。

所以这件事最容易被忽略的地方在于：

**它不是功能错误，而是性能层面的隐藏成本。**

### 6. 这篇文章给出的优化方向

这篇补充文档的关键优化思路，是把“服务端代传对象存储”的模式，调整为更轻量的上传方式。

它强调的方向是：

- 用预签名 URL
- 让上传尽量走真正的流式传输
- 避免让业务服务在对象存储 SDK 里持有大块请求体内存

这类方案的意义在于：

- 业务服务只负责签名和控制
- 文件本体上传不在服务端堆内做大块中转
- 能明显降低单请求的堆内存峰值

### 7. 为什么预签名 URL 值得记住

预签名 URL 的价值，不只是“前端直传对象存储”。

在这篇文章的上下文里，它更重要的意义是：

**把本来由应用服务承担的大文件上传内存压力，转移到更适合处理这件事的对象存储链路上。**

这样做以后，应用服务通常只需要：

- 做参数校验
- 做权限校验
- 生成签名
- 保存元数据

而不必在上传大文件时承担巨大的堆内缓冲压力。

### 8. 这个问题和前面上传接口总结怎么连起来

前面我们已经总结过上传接口本身的职责是：

- 收文件
- 存对象
- 写元数据

现在这篇补充告诉我们，上传接口还有一个隐藏维度：

**上传实现路径本身也要做性能设计。**

也就是说，上传接口不仅要考虑：

- 业务正确性
- 参数校验
- 文件来源类型

还要考虑：

- 上传时有没有大块内存拷贝
- 是否真的走流式
- 大文件下堆占用是否可控

### 9. 这部分最值得记住的点

1. 30MB 文件占到 100MB 内存，通常不是文件本身的问题，而是上传链路中的额外拷贝和缓冲导致的。
2. “API 名字看起来流式”不等于“底层实现真的流式”。
3. 对象存储 SDK 的签名和请求体处理，可能会把文件重新拉回内存。
4. 这类问题很容易被忽略，因为功能没错，只是性能成本高。
5. 预签名 URL 的价值之一，就是把大文件上传的内存压力从业务服务侧挪走。

### 10. 一段适合回头快速看的总结

“30MB 文件为什么会占 100MB 内存”这个问题，本质上是在提醒我们：上传链路里的性能问题，很多时候并不在业务代码表面，而在底层 SDK 的真实实现。哪怕业务代码看起来是流式的，只要对象存储上传路径里存在 payload signing、缓冲拷贝、请求体预构造等行为，就可能产生远高于文件体积本身的堆占用。真正的优化思路不是只盯着 `MultipartFile`，而是要把整个“文件进入服务 -> 对象存储上传”链路看成一个整体，尽量选择更真实的流式路径，必要时用预签名 URL 把大文件上传压力前移或旁路出去。

## 八、文件上传分布式限流如何做？

### 1. 为什么有了大小限制还不够

前面已经有两层保护了：

- 单文件大小限制
- 上传链路的内存优化

但这还只解决了“单个请求”的问题，没有解决“很多请求同时来”的问题。

并发上传时，系统还会面临三类典型风险：

- 临时文件堆积，磁盘空间迅速膨胀
- 临时目录高并发写入，磁盘 IO 被打满
- 上传对象存储时占满网络带宽，拖慢其他业务

所以文件上传一定不能只看单请求大小，还要看：

**集群同时允许多少个上传请求在跑。**

### 2. 为什么不用 QPS 限流

这篇文章特别值得记住的一个结论就是：

**文件上传场景不适合用 QPS 限流。**

原因是 QPS 控制的是“每秒放进来多少请求”，而文件上传是长耗时操作。

比如：

- 限制 `10 QPS`
- 平均每个上传耗时 `30 秒`

那稳态下的实际并发数大致就是：

`10 × 30 = 300`

这时虽然你名义上“限流了”，但实际上还是会同时有 300 个上传在跑，磁盘和 IO 一样扛不住。

所以在上传场景里，真正需要控制的不是请求到达速率，而是：

**同时正在上传的请求数。**

### 3. 这个场景真正需要的是信号量

信号量的语义刚好适合这里：

- 先拿许可
- 拿到才允许开始上传
- 上传结束后释放许可
- 没拿到就等待或失败返回

这样无论单个上传耗时多久，同时占用系统资源的请求数都能被严格卡住。

所以文件上传限流的核心思路可以直接记成：

**不是限“每秒多少个”，而是限“同时多少个”。**

### 4. 为什么需要分布式信号量

单机环境下，用 Java 原生 `Semaphore` 就够了。

但这个项目是集群场景，所以要控制的是：

**整个集群的总上传并发数，而不是某一台机器自己的并发数。**

如果只用本地信号量，会出现这种问题：

- 节点 A 允许 10 个
- 节点 B 允许 10 个
- 节点 C 允许 10 个

结果整个集群就变成了 30 个并发上传，不符合全局保护目标。

所以必须用分布式共享计数器。

### 5. 为什么最终选 Redisson 的可过期信号量

这篇文章对方案选型讲得很清楚，大致经历了三步：

#### 5.1 Java 本地 Semaphore

优点：

- 简单
- 性能好

缺点：

- 只能单机生效
- 集群下不能共享

#### 5.2 Redisson `RSemaphore`

优点：

- 支持分布式
- 集群节点共享计数

缺点：

- 如果实例拿到许可后宕机
- 许可可能永久丢失
- 系统的总并发能力会越来越低

#### 5.3 Redisson `RPermitExpirableSemaphore`

优点：

- 许可自带过期时间
- 节点宕机后会自动回收
- 更适合长耗时上传场景

缺点：

- 需要合理配置过期时间
- 太短会误伤正常请求
- 太长会拖慢异常恢复

所以最终选它的原因很直接：

**既能全局控制上传并发，又能避免宕机造成许可永久泄漏。**

### 6. 这套限流方案怎么落到代码里

文章给出的实现思路很清晰，可以拆成四部分：

#### 6.1 配置类

用于定义：

- 最大并发数
- 最大等待时间
- 许可过期时间

#### 6.2 初始化器

启动时负责：

- 初始化信号量许可数
- 触发历史过期许可的清理或校正

#### 6.3 上传入口

在真正开始上传之前：

1. 先获取许可
2. 获取失败则直接返回友好错误
3. 获取成功后再进入文件上传主流程

#### 6.4 finally 释放许可

无论上传成功还是失败，都在 `finally` 里释放许可。

这是整套方案最关键的一条：

**限流逻辑必须和主流程解耦，但释放动作必须强绑定在 finally。**

### 7. 为什么要在上传之前获取许可

这一点也非常重要。

如果先让请求进入上传主流程，再去限流，就已经晚了，因为：

- 临时文件可能已经写入
- 带宽可能已经开始占用
- IO 压力已经发生

所以正确顺序一定是：

**先拿许可，再开始上传。**

这和前面文档管理、调度抢锁那一套思路其实是很像的，都是“先拿执行资格，再做重活”。

### 8. leaseSeconds 为什么要特别关注

这套方案里最关键的参数之一就是许可过期时间，也就是类似 `leaseSeconds` 这样的配置。

它的作用是：

- 正常上传时，许可被持续持有
- 实例异常退出时，许可在超时后自动回收

这个参数的权衡是：

- 太短：正常慢上传可能被误判过期
- 太长：异常恢复变慢，集群并发能力恢复不及时

所以这个值通常要按：

- 文件大小上限
- 平均上传耗时
- 最慢网络情况

来综合估算。

### 9. 这部分和上传主链路怎么串起来

把它和前面的上传接口结合起来看，完整流程就变成了：

1. 先限流抢许可
2. 再做上传参数校验
3. 再做本地临时文件或 URL 拉取处理
4. 再做对象存储写入
5. 再写数据库元数据
6. 最后释放上传许可

这样系统才真正从“单请求安全”升级到“并发场景安全”。

### 10. 这部分最值得记住的点

1. 文件上传限流控制的核心不是 QPS，而是并发数。
2. 长耗时上传场景下，QPS 限流很容易在稳态下失控。
3. 集群环境需要分布式信号量，而不是本地信号量。
4. `RPermitExpirableSemaphore` 比普通 `RSemaphore` 更适合上传场景，因为它能自动回收异常许可。
5. 获取许可一定要发生在真正上传之前。
6. 许可释放一定要写在 `finally` 里。
7. `leaseSeconds` 是这套方案的关键调优参数。

### 11. 一段适合回头快速看的总结

文件上传分布式限流，本质上是在解决“合规请求太多时，系统照样会被压垮”的问题。单文件大小限制和内存优化只能保证一个上传请求不太离谱，但无法防住大量并发上传导致的临时文件堆积、磁盘 IO 飙升和带宽耗尽。这个场景下最重要的不是控制 QPS，而是控制同时正在上传的请求数，所以最终选型落到了分布式信号量上。相比普通分布式信号量，`RPermitExpirableSemaphore` 更适合上传这类长耗时任务，因为它能在实例宕机后自动回收许可，避免并发能力被永久吃掉。整套方案的核心动作只有一句话：**先拿上传资格，再开始上传；上传结束后，无论成功失败，都释放资格。**

## 九、分布式限流选业务层还是网关层？

### 1. 这个问题为什么很关键

前一篇已经解决了“怎么做分布式上传限流”，但还有一个更本质的问题：

**限流逻辑到底应该放在哪一层，效果才最好？**

因为限流放的位置不同，保护到的资源完全不一样。

比如同样是“拒绝一个上传请求”：

- 放在 Service 层，可能临时文件早就写完了
- 放在 Filter 层，还能拦在 multipart 解析之前
- 放在 Gateway 层，甚至连业务服务线程都不会被占用

所以这篇文章讨论的不是“会不会限”，而是：

**应该在链路的哪个位置限，才最划算。**

### 2. 先记住上传请求的大致处理顺序

这篇文章最关键的前置知识，是 Tomcat 上传请求的处理顺序。

可以概括成：

1. Tomcat 接收连接
2. 分配工作线程
3. 进入 Filter 链
4. 进入 `DispatcherServlet`
5. 触发 multipart 解析
6. 调 Controller / Service

这里最关键的两个时间点是：

- **线程分配发生在 Filter 之前**
- **multipart 解析发生在 Filter 之后、Controller 之前**

这两个时间点几乎决定了整篇文章的结论。

### 3. 为什么 Service 层限流最晚

如果把限流放在 Service 或 Controller 层，那说明请求已经：

- 进入 Spring MVC
- 完成 multipart 解析
- 临时文件已经落盘

这时候你再去判断“当前上传人数太多，不允许上传”，虽然业务上还能拒绝，但资源损耗已经发生了。

所以 Service 层限流的问题是：

- 线程已经占用
- 临时文件已经产生
- 磁盘和 IO 冲击已经发生

因此它几乎解决不了上传场景里最关心的资源保护问题。

结论可以直接记：

**Service 层限流对上传场景基本不推荐。**

### 4. 为什么 Filter 层更适合单体应用

Filter 的价值在于它卡在：

**multipart 解析之前。**

只要在 Filter 里判断上传请求拿不到许可，并且直接返回，不继续 `chain.doFilter()`，那请求就不会继续进入 `DispatcherServlet`，也就不会触发：

- `request.getParts()`
- multipart 解析
- 临时文件写入

这意味着：

- 文件不会真正被解析
- 临时文件不会落盘
- 磁盘和 IO 压力被拦在业务逻辑外面

所以对单体应用来说，Filter 层是一个非常好的限流位置。

### 5. Filter 层还解决不了什么

Filter 也不是完美的。

它虽然能在 multipart 之前拦住请求，但有一个问题仍然存在：

**Tomcat 工作线程已经分配了。**

也就是说，哪怕 Filter 很快返回 429，这个请求在到达 Filter 之前，还是已经占用了一个后端线程。

所以 Filter 层能很好地保护：

- 磁盘
- IO
- 临时文件目录

但对线程池保护没有 Gateway 那么彻底。

### 6. 为什么 Gateway 层更适合微服务

Gateway 的优势在于：

**请求还没进入业务服务，就先被拦下来了。**

在微服务架构里，如果上传并发控制放在 Gateway：

- 业务服务压根收不到超额请求
- 业务服务线程不会被无意义占用
- 业务服务也不会创建临时文件

而且文章还强调了一个很关键的点：

Gateway 基于 Netty/WebFlux，通常只是做流式透传和少量 buffer 处理，不像 Servlet 容器那样在后端服务里先走 multipart 落盘逻辑。

所以在微服务架构里，Gateway 的保护范围更大。

### 7. 三层方案可以怎么对比

可以把三层限流理解成下面这种关系：

#### 7.1 Service 层

- 最晚
- 能挡业务代码执行
- 但挡不住临时文件和 IO

#### 7.2 Filter 层

- 比 Service 更早
- 能挡住 multipart 解析和临时文件
- 但挡不住线程占用

#### 7.3 Gateway 层

- 最早
- 能挡住请求进入业务服务
- 同时保护业务线程和临时文件

所以总原则就是：

**限流越早越好。**

### 8. 为什么说 Filter 和 Gateway 不是互斥关系

这篇文章还有一个很容易被忽略、但特别实用的观点：

**Filter 和 Gateway 不是谁必须替代谁。**

它们可以是分工关系。

比如：

- Gateway 层做总入口并发控制
- Filter 层做业务服务内部兜底

或者：

- Gateway 层按服务总量限流
- Filter 层按用户、知识库、文件类型做细粒度限制

也就是说：

- Gateway 更适合做“入口级总量保护”
- Filter 更适合做“业务级精细控制”

### 9. 单体和微服务怎么选

这篇文章最后给出的结论很直接：

#### 9.1 单体应用

优先选择：

**Filter 层限流**

因为：

- 没有额外网关层可用
- 这是离 multipart 解析最近、同时足够早的拦截点
- 能有效防止临时文件暴涨

#### 9.2 微服务架构

优先选择：

**Gateway 层限流**

因为：

- 请求可以在进入业务服务之前被拦掉
- 业务服务线程、临时文件、磁盘 IO 都能一起保护
- 网关天生就是统一入口，最适合做全局并发控制

如果业务服务内部还需要更细粒度的上传策略，再补一层 Filter 即可。

### 10. 这部分最值得记住的点

1. 上传场景下，限流放在哪一层，比“有没有限流”同样重要。
2. Service 层限流太晚，临时文件和 IO 压力已经发生。
3. Filter 层能拦在 multipart 解析之前，适合单体应用。
4. Filter 层仍然挡不住线程先被 Tomcat 分配。
5. Gateway 层能在请求进入业务服务前完成拦截，适合微服务。
6. Gateway 更偏入口总量控制，Filter 更偏业务细粒度兜底。
7. 总原则是：能往前放，就尽量往前放。

### 11. 一段适合回头快速看的总结

“限流放业务层还是网关层”这个问题，本质上是在回答：系统到底想优先保护哪一类资源。上传请求的关键代价不只是业务代码执行，而是线程占用、multipart 解析、临时文件写入和磁盘 IO，所以限流位置不能只看代码好不好写，而要看资源损耗发生在哪一步。Service 层已经太晚，只能挡住后续业务逻辑；Filter 层能在 multipart 解析之前拦截，适合单体应用；Gateway 层能在请求进入业务服务之前就把它拦住，适合微服务架构。最终结论很清楚：**单体优先 Filter，微服务优先 Gateway；如果需要业务级细粒度控制，再在内部补 Filter 兜底。**

## 十、知识库文档上传接口

### 1. 接口定位

文档上传接口对应知识库接入链路里的“入库阶段”。

它的职责非常明确，只做两件事：

- 把原始文件放到对象存储
- 把文档元信息写入数据库，并返回文档 ID

它不负责真正的 RAG 加工流程，也就是说这里不会直接做：

- 文档解析
- 文本分块
- 向量化
- 向量库写入

所以这个接口本质上是“把文档收进系统”，而不是“把文档处理成可检索状态”。

### 2. 接口定义

- 接口路径：`POST /knowledge-base/{kb-id}/docs/upload`
- 请求格式：`multipart/form-data`

这里之所以不是普通 JSON 接口，是因为它既要收文件，又要收表单参数，因此参数接收方式是：

- `kbId`：路径参数
- `file`：文件部分
- `requestParam`：其余表单字段

接口返回的是文档对象，最关键的是返回文档 ID，后续无论查看状态、开始分块还是重试，都会用到这个 ID。

### 3. 关键参数

上传接口的参数核心分成三组：来源参数、定时参数、处理模式参数。

| 参数 | 含义 | 使用说明 |
| --- | --- | --- |
| `kbId` | 知识库 ID | 路径参数，表示把文档上传到哪个知识库 |
| `file` | 文件对象 | 当来源类型为本地文件时使用 |
| `sourceType` | 来源类型 | `file` 或 `url`，前端必须显式传 |
| `sourceLocation` | 来源地址 | 当 `sourceType=url` 时必传 |
| `scheduleEnabled` | 是否开启定时拉取 | 主要用于 URL 来源文档 |
| `scheduleCron` | 定时表达式 | 开启定时拉取时需要校验 |
| `processMode` | 处理模式 | `chunk` 或 `pipeline` |
| `chunkStrategy` | 分块策略 | `processMode=chunk` 时有效 |
| `chunkConfig` | 分块参数 JSON | `processMode=chunk` 时必传 |
| `pipelineId` | 数据通道 ID | `processMode=pipeline` 时有效 |

从参数设计上就能看出来，这个接口虽然不做真正分块，但会提前把“后面怎么处理”的配置先记下来。

### 4. 来源类型的含义

上传接口支持两种文档来源。

#### 4.1 FILE 来源

`FILE` 表示用户从本地直接选文件上传。

这个场景下：

- 必须带 `file`
- 不需要 `sourceLocation`

可以理解为“用户把文件本体直接交给系统”。

#### 4.2 URL 来源

`URL` 表示用户不是上传文件本体，而是提供一个远程地址，让服务端自己去抓取文件。

这个场景下：

- 必须带 `sourceLocation`
- `file` 可以为空

可以理解为“用户把下载地址交给系统，由系统去远程拉取”。

### 5. 参数校验逻辑

上传接口在真正处理文件之前，会先做参数层面的前置校验。

主要包括以下几类：

#### 5.1 知识库是否存在

系统会先根据 `kbId` 查询知识库。

如果知识库不存在，直接报错，不会继续处理上传逻辑。

#### 5.2 来源类型是否合法

`sourceType` 是必传项，而且只允许合法值。

也就是说：

- 不能为空
- 不能传系统不支持的字符串
- 系统不会帮前端自动猜测来源类型

这个设计是为了让接口语义更清晰，避免后端靠“有 file 就当文件上传”这种隐式规则做推断。

#### 5.3 URL 来源参数校验

如果 `sourceType=url`，那么必须保证：

- `sourceLocation` 有值

否则直接报错。

#### 5.4 定时同步参数校验

如果是 URL 来源，并且开启了定时拉取，那么系统还会继续检查：

- `scheduleCron` 是否为空
- cron 表达式是否合法
- 定时周期是否小于系统允许的最小间隔

这个校验的核心目的，是避免用户配置了不合理的高频同步任务，把系统调度资源打满。

### 6. 文件处理逻辑

上传接口真正的处理重点，在于“怎么把文件安全、可靠地放入对象存储”。

#### 6.1 本地文件上传

如果来源是 `FILE`，处理逻辑比较直接：

1. 接收前端上传的文件
2. 调用文件存储服务上传到对象存储
3. 拿到文件存储地址、文件名、大小、类型等信息

这个分支本质上就是普通的文件入库流程。

#### 6.2 URL 远程抓取

如果来源是 `URL`，处理逻辑会更复杂一些，因为系统需要自己去远程服务器拉文件。

流程大致是：

1. 先尝试发 `HEAD` 请求探测远程文件元信息
2. 判断远程文件是否超出大小限制
3. 再用流式方式下载远程文件
4. 先写入本地临时文件
5. 再从临时文件上传到对象存储
6. 最后删除临时文件

### 7. 为什么 URL 抓取要先落临时文件

这是上传接口里很值得记住的一个工程细节。

系统没有选择“远程流直接转发到对象存储”，而是选择“先写临时文件，再上传”。

这样设计的原因是：

- 一些源站返回的 `Content-Length` 不可靠
- 对象存储上传时通常要求声明长度和真实上传长度严格一致
- 如果直接转发远程流，可能因为长度不准导致上传失败

换句话说，项目这里牺牲了一点本地磁盘 IO，换来了更高的稳定性和兼容性。

这个取舍很务实，也很适合真实生产场景。

### 8. 上传接口的完整执行流程

可以把整个上传接口记成下面这条链路：

1. 根据 `kbId` 查知识库
2. 校验知识库是否存在
3. 解析 `sourceType`
4. 校验来源相关参数
5. 校验 URL 定时同步相关参数
6. 根据来源类型上传文件或抓取远程文件
7. 解析处理模式相关配置
8. 构造文档记录
9. 将文档元信息写入数据库
10. 返回文档 VO 和文档 ID

一句话概括就是：

先把文件放好，再把“这份文件是谁、从哪来、后面怎么处理”这些信息记录下来。

### 9. 上传完成后的状态

上传成功后，文档虽然已经存在于系统中，但通常只是：

- `PENDING`

这个状态的含义是：

- 文件已经进入对象存储
- 文档元数据已经进数据库
- 但还没有开始分块
- 还没有生成向量
- 还没有真正进入可检索状态

这一步非常关键，因为它把“已上传”和“已加工完成”清晰地区分开了。

### 10. 为什么 upload 接口不直接做分块

原因主要有三层。

#### 10.1 职责不同

上传接口的职责是“存文件 + 建记录”，分块接口的职责是“解析 + 分块 + 向量化 + 写库”。

这本来就是两个阶段的事情。

#### 10.2 耗时不同

上传文件一般是秒级，而后续分块和向量化可能是分钟级。

如果把它们硬塞进一个接口里，用户上传一个大文件后就要一直等，体验会很差。

#### 10.3 可维护性更好

拆开后会带来很多好处：

- 用户可以先批量上传，再统一触发分块
- 分块失败后可以直接重试，不必重新上传
- 后续改分块参数时可以重新处理，不必重新传原文件

### 11. 为什么 upload 接口不加大事务

从直觉上看，很多人会觉得“上传文件 + 插数据库”应该包一个事务。

但这个项目故意没有这么做，原因是：

- 对象存储上传属于外部网络 IO
- 这个过程可能比较慢
- 如果数据库事务一直开着等上传完成，会长时间占用数据库连接
- 并发一高，很容易把连接池耗尽

所以项目的思路是：

- 不在事务里做长时间外部 IO
- 接受极少数情况下出现短暂不一致

比如可能出现一种情况：

- 文件已经上传成功
- 但数据库插入失败

这时对象存储里会留下孤儿文件。

项目对此的处理思路不是“强行用长事务解决”，而是：

- 后续通过定时清理任务扫描并清理孤儿文件

这是一种典型的最终一致性设计。

### 12. 这个接口最值得记住的点

如果后面复习上传接口，建议重点记住下面这些：

1. 上传接口只负责入库，不负责分块。
2. 上传成功后文档通常是 `PENDING`，还不可直接用于检索。
3. 来源类型有两种：`FILE` 和 `URL`。
4. URL 来源支持定时拉取，适合在线文档同步。
5. URL 远程抓取采用“先落临时文件，再上传对象存储”的方案。
6. 上传接口不加大事务，是为了避免长事务拖垮数据库连接池。
7. 上传接口已经会把后续处理模式参数一起记录下来。

### 13. 一段适合回头快速看的总结

文档上传接口的本质，是把一份文档正式登记进知识库系统。它先校验知识库和来源参数，再根据 `FILE` 或 `URL` 两种来源完成文件入对象存储，随后把文件名、来源类型、处理模式、分块配置、定时同步配置等元信息写入数据库，并返回文档 ID。上传完成后文档通常处于 `PENDING` 状态，说明文件已经收进系统，但还没开始真正的解析、分块和向量化。这个接口最大的设计特点是职责单一、支持 URL 定时同步、远程抓取更偏稳妥实现，同时避免在事务里执行耗时外部 IO。

## 十一、知识库文档开始分块接口

### 1. 接口定位

开始分块接口对应知识库接入链路里的“加工阶段”。

它的职责不是同步完成整条 RAG 处理链路，而是负责“正式启动文档处理任务”。

它主要做三件事：

- 防止重复触发
- 更新文档状态
- 发出异步处理消息

它不在当前请求线程里做完整分块，而是把重活交给异步消费者处理。

### 2. 接口定义

- 接口路径：`POST /knowledge-base/docs/{doc-id}/chunk`
- 请求参数：只需要 `docId`
- 请求特点：没有请求体，只是触发动作

这说明它不是一个“提交数据”的接口，而是一个“启动任务”的接口。

调用成功后，它会很快返回，并不会等到整个分块和向量化都跑完。

### 3. 这个接口为什么独立存在

开始分块接口单独拆出来，不是为了多做一个接口，而是为了把职责彻底分开。

原因主要有以下几类。

#### 3.1 上传和分块不是一类事情

上传做的是：

- 收文件
- 存文件
- 建记录

分块做的是：

- 解析文件
- 提取文本
- 执行 chunk 切分
- 调 Embedding API
- 写入向量库

前者偏“接收与登记”，后者偏“处理与加工”，天然就应该拆开。

#### 3.2 分块耗时明显更长

一个较大的 PDF 文档，分块链路里可能包含：

- 文件解析
- 多轮文本切分
- 多次 Embedding 请求
- 数据库和向量库写入

这些步骤整体可能比较慢，不适合同步阻塞用户请求。

#### 3.3 拆开以后更灵活

单独拆分块接口之后，可以支持很多更合理的使用方式：

- 先批量上传，再统一触发分块
- 分块失败后单独重试
- 参数调整后重新分块
- 文档内容不变时避免重复上传原文件

### 4. 接口入口与调用方式

这个接口只需要一个 `docId`，说明它的前提是：

- 文档已经通过上传接口成功进入系统
- 系统里已经存在这条文档记录

调用后，服务层会执行 `startChunk(docId)`，但这里的“start”很重要，它表示“启动处理”，不是“同步处理完成”。

### 5. 同步阶段做了什么

开始分块接口的请求线程里只做轻量操作，整体可以称为“同步阶段”。

主要流程如下：

1. 构造分块事件对象
2. 发送 RocketMQ 事务消息
3. 在事务回调中执行本地事务逻辑
4. 成功后立即返回

请求线程里不会直接做：

- 文件解析
- 文本切分
- 向量生成
- 批量写入 chunk

所以用户点击“开始分块”后，响应会很快回来。

### 6. 为什么要先做状态更新

开始分块之前，系统必须先把文档状态切换到处理中。

这是为了表达两件事：

- 当前文档已经进入处理流程
- 后续不能再被重复触发同一轮分块

在这个项目里，状态更新不是普通更新，而是带 CAS 条件的更新。

### 7. 并发控制为什么用 CAS

这里最核心的设计点是用 CAS 控制重复触发。

SQL 语义可以理解为：

```sql
UPDATE t_knowledge_document
SET status = 'running'
WHERE id = ? AND status != 'running'
```

它表达的意思是：

- 只有当前不是 `RUNNING` 的文档，才允许更新成 `RUNNING`
- 如果当前已经是 `RUNNING`，这次更新直接失败

这样就能防住以下场景：

- 用户手抖点两次按钮
- 多个用户同时点击
- 前端因为网络原因重复提交

如果更新条数是 0，系统就会明确提示：

- 文档分块操作正在进行中，请稍后再试

### 8. 为什么不用分布式锁

这个场景没有选 Redis 分布式锁，而是直接用数据库 CAS，原因很务实：

- 目标只是“防重复触发”
- 本质就是状态判断加状态更新
- 一条 SQL 就能完成原子控制

CAS 的优势是：

- 语义更贴场景
- 不需要额外依赖 Redis
- 不引入锁获取、续期、释放等复杂逻辑
- 性能轻量

所以这里不是“独占资源”，而是“当前状态满足条件才允许切换”。

### 9. 为什么要用 RocketMQ 事务消息

如果这里只是简单地“先改状态，再发消息”，会有经典问题：

- 状态改成功了，但消息没发出去
- 消息发出去了，但状态没改成功

这两种情况都会导致系统数据和实际执行行为不一致。

RocketMQ 事务消息的作用，就是把下面两件事绑成一个原子动作：

- 本地事务逻辑成功执行
- 分块消息正式可消费

大致过程可以理解成：

1. 先发半消息
2. 执行本地事务逻辑
3. 本地事务成功则提交消息
4. 本地事务失败则回滚消息

这样能避免最糟糕的一类问题：

- 文档已经变成 `RUNNING`
- 但实际上没人会来处理它

### 10. 本地事务逻辑里除了改状态还做了什么

在事务回调里，除了 CAS 更新状态之外，还做了一件重要的事：

- `scheduleService.upsertSchedule(documentDO)`

这一步的作用，是把文档相关的定时调度配置同步到调度表中。

它尤其适合 URL 来源文档，因为这类文档可能会配置定时拉取、定时更新。

可以把这一步理解为：

- 开始分块时，顺手把这个文档后续自动同步所需的调度信息也维护好

### 11. 请求返回后真正发生了什么

接口请求返回成功，不代表分块已经完成，而是说明“任务启动成功了”。

后续真正耗时的处理，在 MQ Consumer 侧异步进行。

异步阶段通常会做这些事：

1. 拉取文档原始文件
2. 解析文件内容
3. 提取纯文本
4. 按 `processMode` 和 `chunkStrategy` 执行分块
5. 调用 Embedding API 生成向量
6. 把 chunk 数据和向量数据写入持久层
7. 更新文档最终状态
8. 记录本次分块执行日志

所以从系统角度看，开始分块接口只是一个“任务启动器”。

### 12. 用一段话把整个分块流程串起来看

整个分块流程可以理解成这样一条链路：前端调用“开始分块”接口后，服务端不会直接在请求线程里做耗时处理，而是先进入 `startChunk(docId)`，构造分块事件并发送 RocketMQ 事务消息；在这个事务消息的本地事务里，会先用条件更新把文档主表状态从非 `RUNNING` 改成 `RUNNING`，同时记录操作者并同步 schedule，只有这一步事务成功，消息才会被正式提交给 Broker，这样就保证了“文档已经进入运行态”和“后面一定有人来处理这条分块任务”是绑定的；随后 MQ Consumer 异步消费这条消息，进入 `executeChunk(docId)` 和 `runChunkTask(...)` 真正开始执行，并先插入一条分块执行日志，状态同样是 `RUNNING`，用于记录本次分块的开始时间、处理模式、策略、耗时和最终结果；真正处理时会先看文档的 `processMode`，如果是普通 `chunk` 模式，就依次完成文件读取、文本提取、按策略切分 chunk、调用 Embedding 生成向量这几步，如果是 `pipeline` 模式，则交给 ingestion pipeline 做解析、增强、分块等节点编排，最终都产出统一的 `VectorChunk` 结果；拿到 chunk 结果后，系统进入持久化阶段，这一步会用编程式事务把关键写操作包起来：先删除该文档旧的 chunk，再批量写入新的 chunk，接着删除向量库里旧向量，再写入新向量，最后回写文档主表，把 `chunkCount` 更新为新分块数并把状态改成 `SUCCESS`，从而保证 chunk 数据、向量数据和文档主状态保持一致；如果中途任何一步失败，比如文本提取失败、分块失败、Embedding 失败或持久化失败，异常会被统一捕获，文档会被标记为 `FAILED`，分块日志也会更新为 `FAILED` 并记录错误信息，因此从整体上看，这套流程本质上就是“事务消息负责安全启动任务，Consumer 负责异步执行分块，数据库事务负责新旧 chunk 与向量原子切换，主表状态和日志表负责对外体现最终结果”。

### 13. 状态是怎么变化的

开始分块这一段最关键的状态流转是：

1. 上传完成后文档通常是 `PENDING`
2. 调用开始分块后，先切成 `RUNNING`
3. 异步处理结束后，再变成成功或失败状态

这套状态变化有两个好处：

- 前端可以清晰展示文档当前处理进度
- 系统可以据此判断是否允许重试、重复触发或继续加工

### 14. 为什么真正的分块逻辑不包大事务

这一点非常重要。

异步分块链路里有很多重操作：

- 文件 IO
- 文本解析
- chunk 切分
- 外部 Embedding API 调用
- 向量库写入

如果把整个过程都放在一个数据库事务里，会产生明显问题：

- 事务时间过长
- 数据库连接长期占用
- 高并发下容易耗尽连接池
- 还可能增加锁等待和阻塞风险

所以项目采用的原则是：

- 耗时操作全部放在事务外
- 真正需要保证原子性的写入操作才放进事务里

也就是说，事务边界控制得非常精确。

### 15. 原子性真正保证在哪

虽然整条处理链路不包大事务，但项目并没有放弃原子性。

它把最关键的一段原子性要求，集中在“持久化 chunk 和向量数据”这个环节里。

这一步的目标是：

- chunk 表和向量数据要么一起成功
- 要么一起失败

这样可以避免出现下面这种坏情况：

- 文本 chunk 已经写进数据库
- 但对应向量没写进去

或者反过来：

- 向量写进去了
- 但 chunk 元数据没落库

所以项目的设计不是“不要事务”，而是“只在真正需要原子性的时候开事务”。

### 16. 分块日志为什么很重要

开始分块接口背后还有一张很有价值的分块日志表。

它通常记录的信息包括：

- 本次执行状态
- 使用的处理模式
- 使用的分块策略
- 提取耗时
- 分块耗时
- 向量化耗时
- 持久化耗时
- chunk 数量
- 错误信息

这类日志最大的意义有三类。

#### 16.1 性能分析

通过不同阶段耗时，可以快速判断瓶颈在哪：

- 提取慢
- 分块慢
- Embedding 慢
- 写库慢

#### 16.2 故障排查

如果分块失败，日志里通常能直接看到错误信息，比如：

- PDF 解析失败
- Embedding API 超时
- 向量库连接异常

这样排障效率会高很多。

#### 16.3 历史对比

同一份文档后续可能会因为调整分块参数而多次重跑，日志表能保留完整历史，方便横向比较不同参数下的效果和耗时。

### 17. 开始分块接口最值得记住的点

如果后面复习开始分块接口，建议重点记住这些：

1. 这个接口是“启动任务”，不是“同步处理完成”。
2. 它的第一个关键动作是用 CAS 把状态切换为 `RUNNING`。
3. CAS 的目的是防止重复触发，不需要额外上分布式锁。
4. 它通过 RocketMQ 事务消息保证“本地事务”和“消息投递”原子一致。
5. 真正的文档解析、分块和向量化都在异步消费者中执行。
6. 整个分块链路不包大事务，只把必要的持久化操作放进事务里。
7. 分块日志是后续性能分析和问题排查的关键依据。

### 18. 一段适合回头快速看的总结

开始分块接口的本质，是把一份已经上传完成的文档正式送入异步加工链路。它先通过 CAS 把文档状态从非运行中切成 `RUNNING`，防止重复触发，再借助 RocketMQ 事务消息把本地事务和消息投递绑定起来，保证状态更新与任务投递的一致性。请求返回后，真正耗时的文件解析、文本提取、chunk 切分、Embedding 生成、chunk 与向量持久化都在 Consumer 异步完成，最后再更新成功或失败状态并记录分块日志。这个接口最核心的设计思想是异步化、并发可控、消息与状态一致、事务边界精确。

## 十二、深度解析知识库定时同步的架构设计

### 1. 这个机制是干什么的

前面的 `upload` 和 `startChunk` 解决的是“文档怎么进入系统、怎么开始加工”的问题。

但如果文档来源是 URL，就会出现一个新问题：

- 远程文档后续可能持续更新
- 本地知识库中的旧版本会慢慢过时
- 如果每次都靠人工重新上传和重新分块，成本很高，也容易漏掉

所以系统又引入了一条“定时同步”链路。

它的目标很明确：

- 按 cron 周期定时检查远程文档
- 如果远程文档没变化，直接跳过
- 如果远程文档变化了，就自动执行刷新
- 刷新成功后，让知识库里的文档、chunk 和向量都切换到新版本

换句话说，这套机制的本质是：

**让 URL 来源的知识库文档具备自动跟远程源保持同步的能力。**

### 2. 整体链路怎么理解

知识库定时同步不是“一个 cron 定时器 + 一段下载代码”这么简单，它实际上是一整套后台调度机制。

完整链路可以记成：

1. Cron 周期触发扫描器
2. 扫描到期 schedule 任务
3. 多实例竞争任务执行资格
4. 抢到任务后执行变更检测
5. 如果远程文件没变，直接跳过
6. 如果远程文件变了，再抢文档运行权
7. 上传新文件并重新分块、重新生成向量
8. 分块成功后再切换文档元数据
9. 更新调度状态和执行记录
10. 清理旧文件或临时文件

所以这条链路本质上分成三层：

- 调度层：谁该跑
- 互斥层：谁能跑
- 执行层：真正怎么刷新

### 3. 定时同步依赖的数据模型

这套机制的底层不是靠 XXL-JOB 或 Quartz 持久化任务，而是直接依赖数据库里的两张表。

#### 3.1 主表：定时任务表

主表用来描述“这条定时任务是什么、什么时候跑、上次跑得怎么样、现在有没有锁”。

可以把它的字段分成四组。

##### 第一组：基础信息

- `docId`：文档 ID
- `kbId`：知识库 ID
- `cronExpr`：cron 表达式
- `enabled`：是否启用

这一组回答的是：

- 这条任务管的是哪份文档
- 它多久执行一次
- 当前是否生效

##### 第二组：调度状态

- `nextRunTime`
- `lastRunTime`
- `lastSuccessTime`
- `lastStatus`
- `lastError`

这一组回答的是：

- 下次什么时候该跑
- 上次什么时候跑过
- 上次执行结果是什么
- 如果失败，原因是什么

##### 第三组：变更检测字段

- `lastEtag`
- `lastModified`
- `lastContentHash`

这一组回答的是：

- 上一次远程文件的版本指纹是什么
- 下次执行时该拿什么去比对远程文件有没有变化

##### 第四组：分布式锁字段

- `lockOwner`
- `lockUntil`

这一组回答的是：

- 当前这条任务是谁在执行
- 这个执行权多久失效

#### 3.2 子表：执行历史表

除了主表，系统还会记录每次执行的历史。

执行历史表一般会记录：

- 本次执行状态
- 开始时间 / 结束时间
- 文件名 / 文件大小
- 内容哈希
- ETag / Last-Modified
- 消息或失败原因

这张表的价值很大，因为它提供了：

- 执行审计
- 问题排查
- 历史对比
- 跳过原因追踪

所以这套机制不是“执行完就完了”，而是“每次执行都有记录可追”。

### 4. 五个核心组件分别负责什么

这篇定时同步架构文档里，一个很重要的思想就是：**职责分离**。

它没有把所有逻辑塞进一个超大类，而是拆成多个协作组件。

#### 4.1 `KnowledgeDocumentScheduleJob`

它是调度入口，负责：

- 定时扫描待执行任务
- 恢复卡死文档
- 抢第一层 schedule 锁
- 把真正的刷新任务投递到线程池

它不负责真正刷新文件。

所以它更像“派单器”。

#### 4.2 `ScheduleLockManager`

它是锁管理器，负责：

- 抢锁
- 续锁
- 释放锁
- 自动心跳续锁
- 锁丢失检测

它解决的是：

- 多实例下同一条 schedule 同一时刻只能被一个节点执行

#### 4.3 `ScheduleRefreshProcessor`

它是刷新处理器，负责完整刷新流程编排。

它会按顺序决定：

- 什么时候启动心跳
- 什么时候做变更检测
- 什么时候抢文档运行权
- 什么时候上传新文件
- 什么时候执行分块
- 什么时候切换元数据
- 失败后怎么收尾

所以它是整条刷新链路的“总控器”。

#### 4.4 `ScheduleStateManager`

它负责 schedule 主状态和 exec 历史状态的写回。

也就是说：

- 成功怎么记
- 失败怎么记
- 跳过怎么记
- 锁失效时哪些状态不该再写

这部分如果直接散落在主流程代码里，会很乱，所以抽出来是很合理的。

#### 4.5 `DocumentStatusHelper`

它负责文档层面的运行状态辅助控制，比如：

- 文档运行权抢占
- RUNNING 状态恢复
- 分块成功后的文件元数据应用

注意它管的是“文档状态”，不是“schedule 锁状态”。

### 5. 为什么要做分布式锁

只要项目是多实例部署，定时任务就一定会遇到重复执行问题。

因为每个实例都会跑扫描器：

- 实例 A 扫到了这条任务
- 实例 B 也扫到了
- 实例 C 也扫到了

如果没有互斥控制，就会同时发生：

- 重复下载
- 重复分块
- 重复写向量
- 状态互相覆盖

所以必须先解决：

**同一条 schedule，这一轮到底由谁执行。**

### 6. 这里的分布式锁是怎么实现的

它没有用 Redis 锁，也没有引入额外中间件，而是直接基于数据库实现了“租约锁”。

核心就是两个字段：

- `lockOwner`
- `lockUntil`

#### 6.1 抢锁逻辑

抢锁时的语义可以理解成：

```sql
UPDATE t_knowledge_document_schedule
SET lockOwner = '当前实例token',
    lockUntil = now + 锁租期
WHERE id = ?
  AND (lockUntil IS NULL OR lockUntil < now)
```

意思是：

- 只有没有锁，或者旧锁已过期时，才允许当前节点抢到锁

这一步是原子 UPDATE，所以多实例并发抢锁时，只有一个实例会成功。

#### 6.2 为什么 `lockOwner` 不是简单节点名

每次抢锁时都会生成一个唯一 token，而不是只写机器名。

这样做的目的，是让“续锁”和“释放锁”都能严格校验：

- 只有当前真正持有这把锁的那次执行，才能续约或释放

这可以防止误释放别人的锁。

#### 6.3 为什么它是租约锁

因为锁不是永久持有，而是有一个过期时间：

- 到了 `lockUntil` 后，如果没人续锁，这把锁就自动失效

这样即便某个实例执行到一半宕机，也不会造成永久死锁。

后续其他节点等锁过期后，仍然可以接手任务。

### 7. 自动心跳续锁机制

拿到锁并不代表万事大吉，因为定时刷新可能很耗时：

- 下载远程文件
- 上传对象存储
- 重新分块
- 生成 embedding

这些步骤加起来可能持续好几分钟。

如果锁只给固定 15 分钟，不续约的话：

- 长任务可能没执行完
- 锁就先过期了
- 别的节点会把同一个任务再抢走

所以项目引入了自动心跳续锁。

#### 7.1 为什么不用手动续锁

如果让业务代码在每个阶段前手动调一次 `renew()`，会有几个问题：

- 容易忘记
- 续锁时机不好拿捏
- 业务代码会被锁逻辑污染

所以更合理的方式是：

- 获取锁后，启动一个后台心跳线程
- 心跳线程周期性续锁
- 业务代码不用关心续锁细节

#### 7.2 心跳间隔怎么定

项目里的设计思路是：

- 心跳间隔 = 锁租期 / 3
- 但限制在 5~60 秒之间

这是一个经验值平衡：

- 太频繁，数据库压力大
- 太稀疏，来不及补偿失败
- 1/3 一般既安全又不过度浪费资源

#### 7.3 心跳失败怎么办

如果后台续锁失败，说明当前节点已经不再拥有这把锁。

这时系统不会继续装作自己还能执行，而是：

- 标记锁已丢失
- 业务流程在关键阶段检测到后立即中止

这保证了：

- 锁丢失之后不会继续做高成本操作
- 避免两个节点同时把同一任务往下推进

### 8. 为什么业务流程里还要主动检测锁失效

虽然已经有后台心跳，但业务流程里仍然要在关键阶段主动检测锁是否失效。

原因是：

- 心跳是异步的
- 业务线程可能已经推进到高成本阶段
- 如果不主动检查，可能锁已经丢了，但业务还在继续跑

所以项目会在这些关键阶段前检测：

- 抢文档运行权之前
- 执行分块之前

检测思路是两层：

1. 先看心跳线程有没有把锁标记成 lost
2. 再主动调用一次 `renew()` 尝试确认锁还在不在

这个设计非常稳，因为它同时兼顾了：

- 异步心跳感知
- 同步主动确认

### 9. 释放锁为什么也要校验 `lockOwner`

释放锁时不是简单把锁字段清空，而是要带条件：

```sql
UPDATE t_knowledge_document_schedule
SET lockOwner = NULL,
    lockUntil = NULL
WHERE id = ?
  AND lockOwner = ?
```

这样做是为了避免一种很危险的情况：

1. 实例 A 拿到锁，执行很慢
2. 锁过期后，实例 B 抢到了新锁
3. 实例 A 这时才执行完
4. 如果 A 直接清空锁，就会误删 B 的锁

所以释放锁必须校验 `lockOwner`，确保只释放自己持有的锁。

### 10. 为什么需要变更检测

定时同步的目标不是“到时间就重刷一次”，而是：

**有变化才刷新。**

假设你配置每小时同步一次，一天就是 24 次。

但如果远程文档一周才更新一次，那么大部分同步都是无意义的。

如果每次都无脑走完整流程，会浪费：

- 网络流量
- 分块 CPU
- Embedding 成本
- 向量库写入资源

所以必须在真正刷新前先做变更检测。

### 11. 两级变更检测策略

项目里的变更检测不是只靠一个字段，而是做了两级判断。

#### 11.1 第一级：HTTP Header 快速判断

先发 `HEAD` 请求，只取远程资源的 Header，不下载文件正文。

主要看两个标准字段：

- `ETag`
- `Last-Modified`

如果返回值和上次记录一致，就可以快速判断：

- 文件没变化
- 直接跳过

这一层的优点是：

- 快
- 不下载文件
- 大部分没变化场景都能直接短路

但它也有局限：

- 有些服务端不支持 HEAD
- 有些服务端不返回这两个 Header
- 有些服务端 Header 不可靠

#### 11.2 第二级：内容哈希兜底

如果第一层没有命中，就下载文件并计算 SHA-256 内容哈希。

然后和上次存储的 `lastContentHash` 对比：

- 一样：内容没变，跳过
- 不一样：内容变了，继续刷新

这一层的优点是：

- 不依赖远程 Header 的可靠性
- 基于内容本身判断，更准确

这一层的代价是：

- 需要真正下载完整文件
- 需要计算哈希

但相比重新分块和调用 Embedding，它仍然便宜很多。

#### 11.3 为什么这是一个好策略

因为它本质上是：

- 先 cheap check
- 再 expensive check

也就是：

- 能快速判断就尽快跳过
- 快速判断不了，再走精确判定

这比一上来就下载全文要更合理。

### 12. `RemoteFetchResult` 的设计价值

变更检测不是只返回一个布尔值，而是返回一个结果对象。

这个结果对象会带上：

- 是否变化
- 临时文件路径
- 文件大小
- 内容哈希
- ETag
- Last-Modified
- 跳过原因

它还实现了 `AutoCloseable`，这样可以配合 try-with-resources 自动清理临时文件。

这点很重要，因为变更检测过程中会下载临时文件：

- 如果内容没变，要删掉
- 如果异常中断，也不能泄漏临时文件

所以这个设计本质上是：

- 把“结果数据”和“资源生命周期管理”放到一个对象里

这让调用方代码会更干净，也更不容易漏清理。

### 13. 整个定时同步机制最值得记住的点

如果后面复习定时同步机制，建议重点记住这些：

1. 它主要服务于 URL 来源文档，不是本地 FILE 上传文档。
2. 它不是“cron 到点就无脑重刷”，而是“到点后先判断是否变化”。
3. 它底层依赖两张表：任务主表 + 执行历史表。
4. 它通过五个核心组件拆分职责，避免所有逻辑混在一个类里。
5. 它没有用额外中间件锁，而是基于数据库字段实现租约锁。
6. 它用了自动心跳续锁，避免长任务执行时锁提前过期。
7. 它在关键阶段还会主动检测锁是否失效，避免锁丢失后继续执行业务。
8. 它采用两级变更检测：先 Header，再内容哈希。
9. 它只有在确认变化后，才进入重新分块和重新向量化。
10. 它最终追求的是：多实例安全、成本可控、失败可恢复、数据最终一致。

### 14. 一段适合回头快速看的总结

知识库文档定时同步机制，本质上是为 URL 来源文档设计的一套后台自动刷新系统。它以 schedule 主表和 exec 历史表为数据基础，通过调度入口、锁管理器、刷新处理器、状态管理器和文档状态辅助器五个组件分工协作。系统会按 cron 扫描到期任务，先用数据库租约锁保证多实例环境下同一条 schedule 只会被一个节点执行，再用自动心跳维持锁有效性，并在关键阶段主动检测锁是否失效。进入刷新流程后，先用两级变更检测判断远程文件是否真的变化：优先使用 ETag 和 Last-Modified 做快速判断，不命中时再退化到内容哈希比对。只有确认文件变化后，才会重新上传文件、重新分块、重新生成向量，并在成功后更新状态和执行记录。整套机制的核心价值，是让知识库在多实例环境下安全地自动同步远程文档，同时尽量减少无效刷新带来的资源浪费。

## 十三、定时同步的调度引擎与故障恢复

### 1. 调度引擎到底负责什么

如果说前一部分补的是“定时同步依赖哪些基础设施”，那这一部分补的就是：

- 这套机制到底是怎么跑起来的
- 后台线程是怎么调度的
- 执行过程中失败了怎么恢复
- 为什么这套设计在多实例下还能稳定运行

可以把调度引擎理解成：

**负责把 schedule 任务周期性扫描出来，然后像生产者一样把任务投递给执行器，再由执行器完成真正刷新。**

也就是说，它不是简单的单线程 cron 直接把所有事情做完，而是一个“扫描 + 投递 + 异步执行”的调度系统。

### 2. 调度引擎的工作模式

这一篇最大的增量信息之一，是明确了定时同步机制采用的是：

**生产者 - 消费者模式。**

#### 2.1 生产者是谁

生产者就是调度器，也就是 `KnowledgeDocumentScheduleJob.scan()`。

它负责：

- 周期性扫描到期任务
- 从 schedule 表中选出候选任务
- 对每条候选任务尝试抢锁
- 抢到锁后把任务丢给线程池

所以它只管“发现任务、派发任务”，不做真正重处理。

#### 2.2 消费者是谁

消费者就是线程池里的刷新执行逻辑，最终由 `ScheduleRefreshProcessor` 来处理。

它负责：

- 真正执行变更检测
- 抢文档运行权
- 下载新文件
- 重新分块
- 更新状态
- 清理旧文件

也就是说：

- 调度器像“派单员”
- 刷新处理器像“执行员”

#### 2.3 为什么要这么拆

因为如果扫描线程自己同步做完所有事情，会有明显问题：

- 某个刷新任务很慢时，会阻塞后面的任务扫描
- 调度入口和刷新逻辑耦合得非常重
- 整体吞吐量会受单线程限制

拆成生产者 - 消费者模型后，好处是：

- 扫描器能高频、轻量运行
- 真正重任务交给线程池并行消费
- 更适合多实例部署和高延迟远程文件抓取场景

### 3. 调度 SQL 在整个系统里的意义

调度器每轮运行时，核心会查出一批候选任务。

那条 SQL 的核心语义是：

- 只查已启用任务
- 只查已到执行时间的任务
- 只查当前没有被有效锁占用的任务
- 按最早到期优先排序
- 每轮只取一个批量大小

这一层查询的意义不是“直接执行”，而是：

**先把当前有资格进入抢锁流程的任务筛出来。**

真正是不是由当前节点执行，还要靠后面的 `tryAcquire()`。

所以你可以把调度 SQL 理解成“候选队列查询”，而不是最终执行判定。

### 4. 执行流程为什么要拆成三阶段

这一篇对 `ScheduleRefreshProcessor` 的解释更细，明确提出了“三阶段执行模型”。

这很重要，因为它说明这个处理器不是一条直线逻辑，而是一个带阶段边界的状态机。

### 4.1 第一阶段：准备阶段

准备阶段的核心目标是：

**先判断这轮任务值不值得继续往下跑。**

主要动作包括：

- 启动心跳
- 校验任务和文档是否合法
- 创建执行记录
- 执行远程文件变更检测

这一阶段的关键思想是：

- 高成本操作之前，先尽可能把“不该跑的任务”排除掉

比如：

- 文档被删除了
- 文档被禁用了
- cron 非法了
- 定时同步已关闭
- 远程文件没变化

这些情况都不值得继续跑后面的分块和 Embedding。

所以这一阶段本质上是“值不值得跑”的判断阶段。

### 4.2 第二阶段：执行阶段

只有准备阶段确认“值得继续”后，才进入执行阶段。

执行阶段会做的事包括：

- 抢文档运行权
- 上传新文件
- 执行分块
- 等待 chunk / vector 写入完成

这一阶段最关键的特点是：

- 有两层防并发
- 有两次锁失效检测

两层防并发分别是：

- schedule 级别的数据库租约锁
- 文档级别的 RUNNING 状态 / CAS 运行权抢占

这两层结合，才能既防多实例重复调度，又防定时任务和手动分块互相冲突。

两次锁失效检测通常发生在：

- 抢文档运行权之前
- 执行分块之前

这是因为这两个节点都属于高成本或高风险阶段，必须再次确认当前实例还持有锁。

### 4.3 第三阶段：收尾阶段

执行阶段做完后，不代表流程就结束了。

系统还要决定：

- schedule 主表怎么写回
- exec 历史怎么记录
- 新旧文件该怎么清理
- 哪些状态需要保留

这就是收尾阶段。

它的核心目标是：

**让任务执行结果被正确落库，同时保证文件清理不会误删。**

### 5. 为什么需要 `Phase` 阶段追踪

这篇里一个非常值得记住的设计点，就是 `Phase` 的引入。

它的价值不是“让代码好看一点”，而是：

**给 finally 里的清理逻辑提供准确判断依据。**

因为不同阶段失败，能删和不能删的东西完全不一样。

#### 情况 1：还没开始分块就失败

这时：

- 新文件只是临时上传的
- chunk 和向量还没写进去

所以新文件可以直接删除，保留旧文件即可。

#### 情况 2：分块已经成功，但文件元数据还没切过去

这时：

- 新文件已经对应一套新的 chunk 和向量数据
- 只是文档主记录还没完成最终切换

如果这时把新文件删了，就会造成：

- chunk / vector 指向的文件不存在
- 数据不一致

所以这时候新文件不能删，必须保留待后续修复。

#### 情况 3：文件元数据已经切换成功

这时：

- 新文件已经成为正式版本
- 旧文件才应该删

所以 `Phase` 的作用就是：

- 给不同失败位置提供坐标
- 让 finally 能知道现在该删新文件、删旧文件，还是都不删

没有 `Phase`，清理逻辑会变得非常危险。

### 6. 为什么线程池满了要释放锁

调度器在扫描到任务并成功抢到锁后，会尝试把任务提交给线程池。

如果线程池满了，提交会失败。

这时为什么必须立刻释放锁？

因为：

- 当前节点已经抢到了 schedule 锁
- 但任务根本没开始执行
- 如果不释放锁，这条任务会被白白锁住
- 其他节点也拿不到
- 直到锁过期前，这条任务都跑不起来

所以正确做法是：

- 提交失败
- 立刻释放锁
- 让下一轮扫描还能重新尝试

这体现的是一个很实用的原则：

**只有真正开始执行，才配拥有这把锁。**

### 7. 为什么需要 RUNNING 状态故障恢复

除了 schedule 锁自动过期，系统还额外做了一层恢复机制：

- 周期性扫描长期卡在 `RUNNING` 状态的文档
- 超过阈值后，把它重置为 `FAILED`

这一点很重要，因为锁和文档状态不是一回事。

锁负责的是：

- 当前哪台实例能执行 schedule

文档状态负责的是：

- 这份文档当前是否处于处理中

如果实例宕机，可能出现：

- 锁已经自动过期了
- 但文档状态还停留在 `RUNNING`

这时如果不做恢复，这份文档会一直像“处理中”，后续手动操作和自动任务都会受影响。

所以系统做了第二层故障恢复：

- 每分钟扫描一次
- 超过阈值的 RUNNING 文档重置为 FAILED

这能保证文档状态不会永久卡死。

### 8. 双重故障恢复是怎么配合的

整个定时同步的故障恢复，其实是双保险：

#### 第一层：锁自动过期

- 锁有 TTL
- 心跳断了后，锁会自动失效
- 其他实例可以重新接管任务

#### 第二层：RUNNING 状态恢复

- 文档状态长时间停在 RUNNING，会被定时修正为 FAILED
- 用户或系统后续可以重新触发处理

所以即使实例宕机，也不会让任务永远卡死。

你可以把它记成：

- 锁层面靠 lease 自动恢复
- 文档层面靠 RUNNING 扫描自动恢复

### 9. 为什么手动分块和定时同步不会互相冲突

这篇里也把这个问题讲得更清楚了。

系统做了两层防护：

#### 第一层：直接检查文档状态

如果文档当前已经是 `RUNNING`，说明它正在被其他流程处理。

这时定时同步会直接跳过。

#### 第二层：CAS 抢文档运行权

即使第一层检查通过，也还要做一次 CAS 更新：

- 只有当前状态不是 RUNNING，才允许改成 RUNNING

这样就避免了竞态问题：

- 比如你检查时不是 RUNNING
- 但刚准备开始处理时，另一个线程先抢到了运行权

CAS 能确保这里仍然是原子安全的。

所以这套设计不是“靠 if 判断避免冲突”，而是：

- 状态预判 + CAS 原子抢占

### 10. 为什么锁失效时只更新 exec，不强行更新 schedule

这是一个很容易忽略、但非常体现工程思维的细节。

如果锁已经失效，说明很可能：

- 别的实例已经接手了这条 schedule
- 并且已经在更新 schedule 主表状态

这时如果当前实例还去强行写 schedule 主表，就可能覆盖掉别的实例更新的结果。

所以系统的处理思路是：

- 如果 lockOwner 不匹配，就不再更新 schedule 主表
- 但仍然保留 exec 执行历史

这样做的好处是：

- 不破坏当前真正持锁者的主状态
- 同时保留本次执行痕迹，便于排障

也就是说：

- schedule 主表只认当前持锁实例
- exec 历史表可以记录每次执行发生过什么

### 11. 为什么必须保留执行历史表

如果只有 schedule 主表，没有 exec 历史表，你只能看到最近一次的结果。

那就无法回答很多实际问题：

- 这个任务最近一周执行了多少次
- 成功率是多少
- 什么时候最容易失败
- 失败原因都是什么
- 有多少次其实是 SKIPPED

所以 exec 表的价值在于：

- 记录完整历史
- 支持统计分析
- 支持排障追踪

它不是“可有可无的日志表”，而是这套机制可观测性的基础。

### 12. 为什么“分块成功但文件元数据切换失败”时要保留新文件

这也是一个非常工程化的取舍。

如果新文件已经完成了：

- chunk 入库
- vector 入库
- 文档状态也已经成功

只是最后一步“主记录 fileUrl 切换”失败了。

这时删掉新文件会非常危险，因为：

- 数据库里的 chunk / vector 已经基于新文件构建
- 但文件本体却被删掉了
- 最终变成不一致状态

所以系统宁可：

- 多保留一份新文件
- 留给后续人工修复

也不愿意为了节省存储把它删掉。

这其实就是一个典型的故障处理原则：

**优先保证数据一致性，其次才是空间清理。**

### 13. 生命周期管理补充

除了执行流程本身，这篇还补了一个容易忽略的点：schedule 任务不是永久静态存在的，它有生命周期。

大致包括：

- 创建：在 `startChunk` 注册定时任务
- 更新：文档启用/禁用或 cron 变更时同步更新
- 删除：文档删除时级联删除对应 schedule

这说明 schedule 不是一个“旁路小功能”，而是文档生命周期的一部分。

### 14. 配置调优要关注哪几项

这篇提到一个非常实用的点：这套系统有几个关键配置项，需要按实际业务量和执行耗时调优。

重点可以记住这几项：

- 扫描间隔
- 锁持有时间
- 批量大小
- 最小调度间隔
- RUNNING 超时阈值

这些参数的影响分别是：

#### 扫描间隔

控制调度器多久扫一次。

- 太短：数据库扫描更频繁
- 太长：任务触发不够及时

#### 锁持有时间

控制 lease 的基础 TTL。

- 太短：长任务容易在中途过期
- 太长：实例宕机后恢复变慢

#### 批量大小

控制每轮扫描最多取多少任务。

- 太小：吞吐低
- 太大：容易压垮线程池和数据库

#### 最小调度间隔

防止用户把 cron 配得太密，造成高频空跑或高频刷新。

#### RUNNING 超时阈值

决定文档卡多久才被当成异常并恢复。

这个值太短会误伤正常长任务，太长又会拖慢恢复速度。

### 15. 这一部分最值得记住的点

如果后面复习调度引擎和故障恢复，建议重点记住这些：

1. 调度器不是单线程 cron 直接干完，而是生产者 - 消费者模型。
2. 调度 SQL 只查候选任务，真正互斥靠后续抢锁。
3. 刷新处理器的流程是三阶段：准备、执行、收尾。
4. `Phase` 的引入是为了 finally 精准决定删什么文件、保留什么文件。
5. 线程池提交失败必须释放锁，否则任务会白白被占住。
6. 实例宕机后的恢复是双保险：锁自动过期 + RUNNING 状态修复。
7. 手动分块和定时同步不冲突，靠文档状态检查和 CAS 抢运行权双层防护。
8. 锁失效后只更新 exec，不强写 schedule，是为了避免覆盖其他实例状态。
9. exec 历史表是排障、审计和统计分析的基础。
10. 配置调优决定了这套系统能否在实际流量下稳定运行。

### 16. 一段适合回头快速看的总结

定时同步的调度引擎，本质上是一套基于数据库任务表、数据库租约锁和线程池执行器的后台调度系统。它通过生产者 - 消费者模式把“扫描任务”和“执行刷新”拆开，让调度器保持轻量，让执行器专注处理高成本业务。真正刷新时，流程被拆成准备、执行、收尾三个阶段：先确认任务是否合法、值不值得跑，再执行文档运行权抢占、文件刷新和分块，最后根据 Phase 精准决定状态写回和文件清理策略。为了应对实例宕机、锁失效、任务卡死等问题，系统又设计了双重恢复机制：锁靠 lease 自动过期回收，文档状态靠 RUNNING 超时扫描自动修复。整套设计最终实现的是：URL 文档不仅能自动刷新，而且能在多实例、高并发和异常场景下尽量稳定、自愈、可追踪地运行。

## 十四、知识库文档管理接口

### 1. 这组接口主要解决什么问题

上传接口解决的是“把文档放进系统”，开始分块接口解决的是“把文档加工成可检索状态”。

但文档进系统以后，还要继续管理，所以项目又提供了文档级管理接口，主要是三类：

- 删除文档
- 更新文档配置
- 启用/禁用文档

可以把这一组接口理解成：

**文档进入知识库之后的生命周期控制接口。**

### 2. 三个接口整体概览

| 接口 | HTTP 方法 | 路径 | 主要作用 | 典型联动 |
| --- | --- | --- | --- | --- |
| 删除文档 | `DELETE` | `/knowledge-base/docs/{doc-id}` | 删除文档及其关联数据 | chunk、schedule、chunk_log、vector、文件 |
| 更新文档 | `PUT` | `/knowledge-base/docs/{docId}` | 更新文档配置和处理参数 | schedule 配置同步 |
| 启用/禁用文档 | `PATCH` | `/knowledge-base/docs/{docId}/enable` | 切换文档可用状态 | schedule、chunk、vector 联动 |

这三个接口有一个共同前提：

**文档不能处于 `RUNNING` 状态。**

因为一旦文档正在分块、刷新或向量化，如果此时又删、又改、又切状态，就很容易产生并发冲突和脏数据。

### 3. 三个接口的共同设计思想

虽然 delete、update、enable 的业务语义不同，但它们的共同设计思想非常一致：

#### 3.1 都不是只改一张主表

它们本质上都涉及多表联动，比如：

- `t_knowledge_document`
- `t_knowledge_chunk`
- `t_knowledge_document_schedule`
- `t_knowledge_document_chunk_log`
- `t_knowledge_vector`

所以这些接口的本质都不是“单表 CRUD”，而是：

**围绕文档主表做的一组级联状态变更。**

#### 3.2 都要考虑向量库一致性

在这个项目里，真正检索时查的是向量库，不是只查文档表。

所以：

- 文档删除，不能只删主表，向量也要删
- 文档禁用，不能只改 `enabled=0`，向量也要删
- 文档启用，不能只改 `enabled=1`，向量还得重建

#### 3.3 都要考虑事务边界

这几个接口背后都体现了一个工程判断：

- 短小、纯写库操作，适合 `@Transactional`
- 方法中含较长外部 IO 或 embedding，适合编程式事务精确包裹

### 4. delete 接口完整总结

`DELETE /knowledge-base/docs/{doc-id}`

这个接口的目标是：**安全地下线并删除一整份文档。**

核心流程可以记成四步：

1. 查询文档主记录，校验存在性
2. 如果文档处于 `RUNNING`，直接拒绝删除
3. 在事务里清理数据库关联数据
4. 事务外尽力删除对象存储里的源文件

#### 4.1 事务内会处理哪些数据

主要包括：

- 删除该文档的所有 Chunk
- 删除该文档对应的 schedule
- 删除该文档的分块日志
- 主表做逻辑删除或删除标记更新
- 删除该文档的向量数据

这部分的重点是：

**数据库关联数据必须要么一起成功，要么一起失败。**

#### 4.2 为什么文件删除要静默失败

对象存储文件删除不属于数据库事务的一部分，所以项目选择的是：

- DB 强一致
- 文件删除最终一致

也就是：

- 数据库删成功最重要
- 文件删不掉最多残留一个孤儿文件
- 可以靠日志和后续清理任务兜底

这是一种典型的工程取舍。

#### 4.3 delete 接口最值得记住的点

- 它是文档级最强破坏性操作
- 它会级联清理很多关联数据
- 它先保证数据库一致性，再接受文件侧最终一致

### 5. update 接口完整总结

`PUT /knowledge-base/docs/{docId}`

这个接口的核心不是重新分块，而是：

**更新文档的配置、元信息和后续处理参数。**

它的复杂点在于：文档有些字段改完只是更新元数据，但有些字段改完会影响后续处理逻辑，比如：

- `chunkStrategy`
- `chunkConfig`
- `processMode`
- `pipelineId`
- `scheduleCron`
- `scheduleEnabled`

所以 update 接口要解决两个问题：

1. 哪些字段允许改
2. 改完后哪些关联配置要同步

#### 5.1 它为什么不是“重新分块接口”

update 接口的职责是改配置，不是立即重跑任务。

也就是说：

- 你更新了文档配置
- 不代表系统马上重新切 Chunk
- 也不代表马上重建向量

真正重分块还是由专门的分块链路触发。

这样做的好处是：

- 配置变更和重任务执行解耦
- 接口更轻
- 职责更清晰

#### 5.2 它为什么也要检查 RUNNING

因为如果文档已经在跑分块，这时再改配置，就会出现：

- 当前任务用旧配置
- 主表已经写成新配置
- 最终结果和表里配置对不上

所以更新接口必须在文档空闲时才能执行。

### 6. enable 接口完整总结

`PATCH /knowledge-base/docs/{docId}/enable`

这个接口看起来像“改一个开关”，其实比表面复杂得多。

它的本质是：

**同步切换文档、Chunk、调度任务、向量库的可用状态。**

#### 6.1 禁用时做什么

禁用文档时，通常会一起做四件事：

1. 文档主表 `enabled = 0`
2. schedule 状态同步关闭或暂停
3. 该文档下所有 Chunk 的 `enabled = 0`
4. 删除该文档在向量库里的所有向量

这样做的原因很直接：

如果只改文档表，不删向量，那检索时还是会命中这篇文档，禁用就没有真正生效。

#### 6.2 启用时做什么

启用文档时，会走相反分支：

1. 读取该文档下已有 Chunk
2. 重新做 embedding
3. 文档主表 `enabled = 1`
4. schedule 状态同步恢复
5. 批量把 Chunk 的 `enabled = 1`
6. 把向量重新写回向量库

所以启用不是简单改个状态位，而是：

**恢复文档的检索能力。**

#### 6.3 为什么这里要用编程式事务

因为启用时要做 embedding，而 embedding 往往最耗时。

如果整段逻辑都用 `@Transactional`，会导致：

- 数据库事务时间很长
- 连接被长时间占用
- 并发能力下降

所以项目里采用的是：

- 事务外先查 Chunk、先算 embedding
- 再用 `TransactionOperations` 把主表更新、Chunk 更新、schedule 同步、向量写入包成一个短事务

这是一个非常典型的编程式事务使用场景。

### 7. 文档级接口里 deleted、enabled、status 怎么配合

文档管理接口复习时，这三个字段也很容易混。

最简单的记法是：

- `deleted`
  - 这条文档记录还算不算存在
- `enabled`
  - 这条文档现在能不能参与业务
- `status`
  - 这条文档当前正在经历什么处理阶段

把它们套进三个接口里理解会更清楚：

- delete
  - 核心看 `deleted`
- enable
  - 核心看 `enabled`
- delete / update / enable
  - 执行前都要看 `status`，尤其是不能为 `RUNNING`

### 8. 文档级接口和 Chunk 级接口的关系

这也是一个很适合回头复习的问题。

可以这样理解：

- 文档级接口控制的是“整份文档”
- Chunk 级接口控制的是“文档内部片段”

两者联动关系是：

- 文档启用/禁用时，会批量影响 Chunk 的 `enabled`
- 文档删除时，会级联删除或清理 Chunk
- 但单条 Chunk 的增删改查，不会反过来改变文档主状态

也就是说：

**文档是上层聚合对象，Chunk 是下层组成单元。**

### 9. 这一部分最值得记住的点

1. 文档管理接口解决的是文档入库之后的生命周期控制问题。
2. delete、update、enable 都不是单表操作，而是多表联动。
3. delete 是破坏性最强的接口，重点是级联清理和事务一致性。
4. update 的职责是改配置，不是立即重分块。
5. enable 看起来最轻，实际隐藏了 Chunk、schedule、vector 的三级联动。
6. 向量层没有 `enabled` 状态位，启用/禁用靠“重建向量 / 删除向量”体现。
7. enable 用编程式事务，是为了把 embedding 这种耗时步骤挪到事务外。

### 10. 一段适合回头快速看的总结

知识库文档管理接口，本质上是在补齐“文档进入系统之后怎么安全演化”的能力。delete 负责完整下线和清理，update 负责调整配置和处理参数，enable 负责切换文档的在线状态。它们三个共同体现的设计思想是：主表状态不能孤立看，必须同时考虑 Chunk、调度任务、向量库和对象存储；短操作用声明式事务，长链路里含 embedding 的操作用编程式事务；数据库一致性优先保证，文件系统和外部资源接受最终一致。把这三条链路理顺之后，文档从上传、分块、定时刷新，到删除、更新、启用/禁用，完整生命周期就基本串起来了。

## 十五、知识库数据分块管理接口

### 1. 这一组接口是干什么的

文档级接口解决的是“整份文档”的生命周期管理，比如上传、开始分块、删除文档、启用文档。

但真正参与检索的是 Chunk，所以系统还提供了一组更细粒度的 Chunk 管理接口，目的是让我们在自动分块结果不理想时，可以对具体片段做精准干预，而不是每次都重跑整份文档。

这组接口本质上是：

- 给自动分块结果提供人工修正入口
- 允许对单条或批量 Chunk 做增删改查
- 允许对 Chunk 做启用/禁用控制
- 保证 Chunk 表、文档计数、向量库三者尽量一致

### 2. 六个接口整体概览

这一组接口一共 6 个：

| 接口 | HTTP 方法 | 路径 | 主要作用 | 向量联动 |
| --- | --- | --- | --- | --- |
| 分页查询 | `GET` | `/knowledge-base/docs/{doc-id}/chunks` | 按文档查看 Chunk 列表 | 无 |
| 新增 Chunk | `POST` | `/knowledge-base/docs/{doc-id}/chunks` | 手动补一条新 Chunk | 写入向量 |
| 更新 Chunk 内容 | `PUT` | `/knowledge-base/docs/{doc-id}/chunks/{chunk-id}` | 修改单条 Chunk 文本 | 更新向量 |
| 删除 Chunk | `DELETE` | `/knowledge-base/docs/{doc-id}/chunks/{chunk-id}` | 删除单条 Chunk | 删除对应向量 |
| 启用/禁用单条 | `PATCH` | `/knowledge-base/docs/{doc-id}/chunks/{chunk-id}/enable` | 切换单条 Chunk 可用状态 | 按需写入或删除向量 |
| 批量启用/禁用 | `PATCH` | `/knowledge-base/docs/{doc-id}/chunks/batch-enable` | 批量切换状态 | 批量写入或删除向量 |

可以把这 6 个接口记成两类：

- “内容管理”：查询、新增、更新、删除
- “状态管理”：单条启用/禁用、批量启用/禁用

### 3. 这组接口里最关键的三个字段

复习 Chunk 管理接口时，一定要把这三个字段分清：

- `deleted`：表示这条 Chunk 记录还在不在
- `enabled`：表示这条 Chunk 现在允不允许参与业务
- `status`：主要在文档层，表示文档当前是否处于 `RUNNING` 等处理中状态

Chunk 管理最容易混淆的地方是：

- 删除 Chunk，才会涉及 `deleted`
- 启用/禁用 Chunk，改的是 `enabled`
- 文档正在 `RUNNING` 时，很多 Chunk 操作都会被拒绝

一句话记忆：

**删除是生命周期问题，启用是可用状态问题，RUNNING 是运行时并发保护问题。**

### 4. 分页查询接口在做什么

`GET /knowledge-base/docs/{doc-id}/chunks`

这个接口很轻，主要就是：

1. 校验文档存在
2. 按 `docId` 查询 Chunk
3. 支持按 `enabled` 过滤
4. 按 `chunkIndex` 排序后分页返回

它不改任何数据，也不碰向量库。

它存在的价值主要是：

- 给前端展示当前文档的分块结果
- 支持筛选启用/禁用状态
- 作为后续编辑、删除、启用/禁用的前置查看入口

### 5. 新增 Chunk 接口的完整含义

`POST /knowledge-base/docs/{doc-id}/chunks`

这个接口不是简单插一条文本，而是“新增一条立即可参与检索的 Chunk”。

核心流程可以记成：

1. 先校验文档存在
2. 校验文档不能处于 `RUNNING`
3. 校验文档本身必须是启用状态
4. 计算 `chunkIndex`
5. 计算 `contentHash`、`charCount`、`tokenCount`
6. 插入一条新 Chunk
7. 更新文档的 `chunk_count`
8. 对内容做 embedding
9. 把向量写入向量库

所以新增接口的特点是：

- 默认新 Chunk 是 `enabled = 1`
- 新增成功后马上可被检索
- 它不仅改业务表，还会改向量表

### 6. 更新 Chunk 内容接口要怎么理解

`PUT /knowledge-base/docs/{doc-id}/chunks/{chunk-id}`

这个接口非常值得单独记，因为很多人会把它理解成“删旧插新”，但在当前项目代码里，更准确的说法是：

- **Chunk 主表层面：原记录更新**
- **向量层面：重算 embedding 后做覆盖更新 / upsert**

它的核心流程是：

1. 校验文档存在，且不能是 `RUNNING`
2. 校验 Chunk 存在，且归属当前文档
3. 如果新内容和旧内容完全一样，直接返回
4. 更新当前 Chunk 的 `content`
5. 重新计算 `contentHash`、`charCount`、`tokenCount`
6. `updateById` 更新原记录
7. 重新生成 embedding
8. 调用 `vectorStoreService.updateChunk(...)` 更新向量

这里有两个特别值得记住的点：

#### 6.1 内容没变就直接返回

这是一个很实用的优化，因为：

- embedding 可能按 Token 计费
- 无变化更新纯属浪费
- 还会多做一次向量写入

#### 6.2 文档里说“删旧插新”，要怎么理解

如果按业务语义理解，内容一变，旧向量就失效了，新向量要替代旧向量，所以很多文章会把它概括成“删旧插新”。

但结合当前仓库代码，更严谨的说法是：

- Chunk 表不是 `delete + insert`
- 当前代码用的是 `chunkMapper.updateById(...)`
- PGVector 用的是 `INSERT ... ON CONFLICT DO UPDATE`
- Milvus 用的是 `upsert`

所以复习时最好这样记：

**业务语义上是“旧向量失效、新向量顶替”；代码实现上是“更新原 Chunk + upsert 向量”。**

### 7. 删除 Chunk 接口的完整含义

`DELETE /knowledge-base/docs/{doc-id}/chunks/{chunk-id}`

这个接口才是真正和 `deleted` 强相关的接口。

核心流程：

1. 校验文档存在，且不能是 `RUNNING`
2. 校验 Chunk 存在且归属当前文档
3. 删除该 Chunk 记录
4. 文档 `chunk_count - 1`
5. 从向量库删除该 Chunk 对应向量

这里最关键的是：

- `KnowledgeChunkDO` 上有 `@TableLogic`
- 所以 `deleteById` 通常语义上对应逻辑删除
- 也就是把 `deleted` 置为 `1`

因此这个接口的本质是：

**逻辑删除 Chunk 记录 + 物理删除该 Chunk 的向量。**

### 8. 单条启用/禁用接口在做什么

`PATCH /knowledge-base/docs/{doc-id}/chunks/{chunk-id}/enable`

这个接口改的不是 `deleted`，而是 `enabled`。

两条分支要分开记：

#### 8.1 禁用时

- 把该 Chunk 的 `enabled` 改成 `0`
- 从向量库删除这条 Chunk 的向量

#### 8.2 启用时

- 把该 Chunk 的 `enabled` 改成 `1`
- 重新做 embedding
- 把向量重新写回向量库

所以它本质上不是“恢复已删除数据”，而是：

**切换 Chunk 是否参与检索。**

### 9. 批量启用/禁用为什么用编程式事务

`PATCH /knowledge-base/docs/{doc-id}/chunks/batch-enable`

它和单条启用/禁用逻辑类似，但因为一次可能处理很多 Chunk，所以设计上更强调事务边界控制。

核心原因是：

- 批量 embedding 比较耗时
- 如果整个方法直接用 `@Transactional`
- 那数据库事务会把 embedding 这段外部耗时也包进去
- 事务时间过长，数据库连接占用会明显变差

所以这里采用的思路是：

1. 事务外先准备需要启用的 Chunk 列表
2. 事务外先算好 embedding
3. 再用 `TransactionOperations` 只包住真正的 DB 更新和向量写入

也就是：

**耗时计算放事务外，关键写库放事务内。**

### 10. Chunk 管理接口里哪些场景会碰到 deleted

这是一个非常适合回头复习的问题。

结论可以直接记住：

- `pageQuery`：不碰 `deleted`
- `create`：插入新记录，默认 `deleted = 0`
- `update`：更新原记录，不碰 `deleted`
- `enableChunk` / `batchEnable`：改 `enabled`，不碰 `deleted`
- `delete`：会碰 `deleted`
- `deleteByDocId`：整篇文档重分块或文档删除时，会批量碰 `deleted`

也就是说，真正容易出现“删旧插新”的场景，不是单条 `updateChunk`，而是：

- 整篇文档重分块
- 定时刷新后内容发生变化
- 手动重新开始分块

这些场景往往会：

1. 批量逻辑删除旧 Chunk
2. 批量插入新 Chunk
3. 删除旧向量
4. 写入新向量

### 11. 这一部分最值得记住的点

1. Chunk 管理接口存在的意义，是给自动分块结果提供“精修能力”。
2. `deleted` 表示记录是否存在，`enabled` 表示记录是否参与业务。
3. 单条 Chunk 更新不是删旧插新，而是更新原记录并覆盖更新向量。
4. 删除 Chunk 才是逻辑删除，才和 `deleted` 直接相关。
5. 启用/禁用 Chunk 本质是“向量写入/删除联动”。
6. 批量启用/禁用用编程式事务，是为了把耗时 embedding 挪到事务外。
7. 整篇文档重分块才是更典型的“旧 Chunk 批量失效、新 Chunk 批量建立”场景。

### 12. 一段适合回头快速看的总结

知识库数据分块管理接口，本质上是一组“自动分块后的精细化修正接口”。它不替代自动分块，而是给系统补上一层人工干预能力：当某一条 Chunk 内容不合适、需要补充、需要删除、需要临时下线时，用户不必重跑整篇文档，而可以直接操作具体 Chunk。整组接口的核心设计思想是三件事：第一，内容层面的变更要同步到向量库；第二，删除和启用/禁用要明确区分 `deleted` 与 `enabled`；第三，批量操作要通过编程式事务缩短事务持有时间。理解了这一层，就能把“文档级管理”和“Chunk 级管理”彻底分开。
