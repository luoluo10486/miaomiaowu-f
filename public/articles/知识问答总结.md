# 知识问答总结

## 一、记忆服务的完整链路

记忆服务的核心职责是：**把旧历史加载、当前消息落库、长对话压缩摘要这三件事收拢到同一条链路里，给后面的改写、意图识别和检索稳定提供上下文。**

主要链路：

1. **入口先读再写**：`StreamChatPipeline.loadMemory(ctx)` 不自己查库，而是统一调 `memoryService.loadAndAppend(...)`；`loadAndAppend` 固定先 `load` 再 `append`，避免当前这条用户消息被重复塞进 Prompt。
2. **加载时并行取摘要和历史**：`load(...)` 内部并行执行 `loadSummaryWithFallback(...)` 和 `loadHistoryWithFallback(...)`，目标是把总耗时压到接近两者中的较大值；摘要失败降级成 `null`，历史失败降级成空列表。
3. **历史不是全量，而是滑动窗口**：`JdbcConversationMemoryStore.loadHistory(...)` 只取最近几轮 `user/assistant` 消息，查库时按时间倒序截取，取回后再反转成正常顺序，并修掉开头孤立的 `assistant` 消息。
4. **摘要和历史最后合并成一份记忆上下文**：如果两者都有，就把摘要先包装成一条 `SYSTEM` 消息放最前面，再接最近几轮原文历史，形成“长期摘要 + 近期原文”的组合记忆。
5. **当前消息先落库，再异步触发压缩检查**：`append(...)` 先把消息写入消息表，`USER` 消息顺手更新会话活跃时间；真正触发压缩检查的是 `ASSISTANT` 消息，因为它代表一轮对话闭环。
6. **摘要压缩不会阻塞主流程**：`summaryService.compressIfNeeded(...)` 在异步线程里执行，先抢会话级锁，再根据 `summaryStartTurns`、`historyKeepTurns` 和上次摘要的 `lastMessageId` 算出本次该压哪段旧消息。
7. **摘要 Prompt 也是结构化组装**：顺序通常是“摘要规则模板 -> 旧摘要（如果有）-> 待压缩原始消息 -> 最后一条用户指令”，再调 `llmService.chat(...)` 生成新摘要，并把摘要内容和新的 `lastMessageId` 一起落库。
8. **最终注入问答 Prompt 时，顺序是摘要、历史、当前问题**：也就是先给长期背景，再补近期细节，最后聚焦本轮用户问题。
9. **记忆服务后面紧接着就是查询改写**：因为这份上下文不是答案，而是给 `rewriteWithSplit(question, history)` 提供输入，让系统先把“适合聊天理解的话”改成“适合检索处理的话”。
10. **查询改写先做术语归一化，再决定要不要调 LLM**：开关关闭就走规则拆分兜底；开关开启就把改写模板、最近一两轮历史和当前问题组装成消息，调一次 LLM 同时拿到 `rewrittenQuestion` 和 `subQuestions`。
11. **改写结果还要经过 JSON 清洗和解析**：只有结构合法才算成功；如果 LLM 调用异常或解析失败，就统一降级成 `new RewriteResult(normalizedQuestion, List.of(normalizedQuestion))`，保证下游永远消费统一结构。

一句话总结：**这一章的主线就是先把“历史拿准”，再把“问题改准”，让后面的意图识别和检索拿到一份既连贯又可搜索的输入。**

## 二、意图识别的完整链路

意图识别的核心职责是：**把上一层改写后的问题结构，变成一组可以直接驱动下游检索、工具调用或系统直答的候选意图集合。**

主要链路：

1. **入口先接 `RewriteResult`**：`IntentResolver.resolve(...)` 不再重新理解整段历史，只关心当前有哪些子问题；如果 `subQuestions` 为空，就回退到 `rewrittenQuestion` 作为唯一子问题。
2. **多个子问题并行分类**：每个子问题都会在 `intentClassifyExecutor` 线程池里异步执行 `classifyIntents(q)`，最后 `join()` 汇总成 `List<SubQuestionIntent>`；单个子问题失败会在子任务内部降级成空意图，不拖累整体请求。
3. **单题分类前先加载运行时意图树**：`DefaultIntentClassifier` 先走 `loadIntentTreeData()` 读 Redis；Redis 没有就回源数据库重建整棵树，再得到 `allNodes`、`leafNodes` 和 `id2Node`。
4. **真正喂给 LLM 的是叶子节点清单**：分类器会把每个叶子节点的 `id`、`path`、`description`、`examples`，以及可选的 `type/toolId` 拼成一份紧凑的 `key=value` 文本，不直接把整棵树原样发给模型。
5. **Prompt 模板按需加载并渲染**：`buildPrompt(...)` 会调 `promptTemplateLoader.render(...)`，把 `{intent_list}` 替换成叶子节点清单；模板文件第一次用到时才从 `classpath` 读出，后面走内存缓存。
6. **模型看到的是“规则 + 候选 + 当前子问题”**：完整 `systemPrompt` 负责告诉模型怎么判断、怎么打分、怎么输出 JSON，当前子问题再作为 `USER` 消息补进去，调用参数也会故意调保守，保证分类结果更稳定。
7. **LLM 返回后还要做程序化解析**：先清理 markdown code fence，再解析 JSON 数组或 `results` 包装结构；每条结果里的 `id` 会查回真实 `IntentNode`，未知 `id` 或解析异常都直接跳过或降级成空结果。
8. **单题结果先做阈值过滤，再做数量限制**：`classifyIntents(question)` 会先按 `INTENT_MIN_SCORE` 丢掉低分候选，再按 `MAX_INTENT_COUNT` 限制单个子问题的意图数，避免大量弱相关候选继续往后传。
9. **多子问题场景还要再做一次全局封顶**：`capTotalIntents(...)` 解决的是“多个子问题加起来意图太多”的问题；它会先保证每个子问题至少保留一个最高分意图，再让剩余名额按全局分数竞争。
10. **全局封顶靠 `IntentCandidate` 做中间过渡**：候选先被临时拍平成 `IntentCandidate(subQuestionIndex, nodeScore)` 方便全局排序，最后再通过 `rebuildSubIntents(...)` 按原始子问题顺序重建回 `List<SubQuestionIntent>`。
11. **结果输出后，下游可以直接按类型分流**：`mergeIntentGroup(...)` 会把命中的节点按 `kind=KB/MCP/SYSTEM` 拆开，因为 `IntentNode` 在分类结果里已经是完整节点对象，不需要下游再猜类型。

一句话总结：**这一章的主线就是先把“候选节点列清楚”，再把“每个子问题最该去哪里”判出来，最后把结果压到一个下游还能稳定消费的规模。**

## 三、歧义引导的完整链路

歧义引导的核心职责是：**当候选意图已经出来，但系统还没足够把握直接选一个方向时，先反问用户，而不是贸然检索错库。**

主要链路：

1. **它处在意图识别之后、正式检索之前**：前一层已经产出了收敛过的 `List<SubQuestionIntent>`；歧义引导要判断的不是“有没有意图”，而是“这些意图里有没有不能安全直接选的情况”。
2. **它解决的是“意图太像”，不是“意图太多”**：总量封顶解决的是多个子问题加起来候选太多；歧义引导解决的是同一个子问题下前两名太接近，比如“退货政策”同时像 3C、家电和服装。
3. **真正比较前，系统会先往上归并到更适合交互的层级**：不会直接把一堆叶子节点展示给用户，而是从叶子节点往上回溯到 `CATEGORY`，把“3C 数码”“家电”“服装”这类类别当作引导选项。
4. **第一层先走快速跳过**：如果第一名已经明显甩开第二名，或者用户问题里已经明确出现了品类名、系统名这类显式线索，就直接放行，不触发引导。
5. **正式判定看的是前两名分数比值**：系统用 `ratio = second / top` 作为核心信号，再把它分成“明确歧义、灰色地带、明确不歧义”三个区间；明显场景交给规则，边界场景交给模型补判断。
6. **灰色地带才会调 `AmbiguityLLMChecker`**：这一步不会再把整棵树丢给模型，只给当前问题和少量候选类别，让模型回答“这到底算不算歧义”；参数也会故意调保守，保证结果稳定。
7. **如果二次确认失败，系统更倾向于保守**：也就是宁可多问一次，也不要直接选错方向继续往后查；这和前面意图识别层“宁可空结果也别错路由”的思路是一致的。
8. **判定结果最后收敛成 `GuidanceDecision`**：常见状态只有 `NONE` 和 `PROMPT`；前者表示继续正常流程，后者表示已经准备好一段可直接发给用户的引导文案。
9. **引导文案通常走模板渲染，不现场自由生成**：比如 `guidance-prompt.st` 里放主题名和候选类别列表，并限制最多展示几个选项，目标是稳定、可控、用户一眼能选。
10. **一旦决定引导，Pipeline 会在这里直接短路**：它通过现有 SSE 回调把引导文案推给前端，然后结束本轮请求，后面的检索、重排序和 RAG 生成都会跳过。
11. **用户做完选择后，会作为下一轮消息重新进入完整链路**：会话记忆会把上一轮引导和用户选择带回来，查询改写再把“1”“3C 数码”这种短回复补全成更明确的问题，通常就不会再次重复引导。

一句话总结：**这一章的主线就是先判断“现在能不能安全直接选”，不能就反问用户，把错误检索拦在真正生成答案之前。**

### 3.1 歧义引导如果没触发，后面怎么继续

1. `GuidanceDecision = NONE` 时，Pipeline 不会停在这里，而是把当前问题继续交回正常链路。
2. 下一步通常还是先把会话记忆、当前轮上下文和用户刚补充的限定词一起带上。
3. 然后继续走查询改写、意图识别、总量封顶、检索和生成。
4. 所以歧义引导不是一条独立的“支线”，而是八阶段主链路里的一个可短路分支。

### 3.2 歧义引导如果触发了，下一轮为什么还能顺回来

1. 触发 `PROMPT` 后，这一轮会先结束，后续检索和生成都不再执行。
2. 用户的选择会进入会话记忆，成为下一轮可用的历史上下文。
3. 下一轮查询改写会把“1”“3C 数码”这种短回复补全成更明确的问题。
4. 一旦问题已经带上明确类别，前面的快速跳过逻辑通常就会直接放行，不会重复引导。
5. 这就形成了“先问清楚，再回到主链路继续跑”的闭环。

### 3.3 歧义引导之后，后面四个阶段在代码里怎么跑

1. 如果 `handleGuidance(...)` 没有短路，`StreamChatPipeline.execute(...)` 就会继续往后走。
2. 后面的四个阶段会在下一章继续展开，分别是系统直答、多通道检索、空结果兜底和 Prompt 组装。
3. 这一步只是把分支接回主链路，真正的具体实现要看下一章。

## 四、歧义引导后，后面四个阶段怎么继续跑？

这一章承接第三章，讲的是歧义引导没有把请求截停之后，Pipeline 怎么继续往后跑。核心问题不是“还要不要再问一次”，而是：一旦用户已经给出了足够明确的信息，后端接下来怎么在系统直答、检索、兜底和生成之间顺着走完后续链路。

### 1. 阶段 5：系统直答

系统直答这一段的目标很明确，就是把“根本不需要检索”的问题从重链路里提前摘出来。它的入口不是随便猜，而是先通过 `intentResolver.isSystemOnly(...)` 做严格判断：只有当前子问题里真的只剩一个 `SYSTEM` 节点，Pipeline 才会把请求送进系统直答分支。只要还有 KB 或 MCP 意图，这里就不会短路，因为这类问题本质上还是应该继续找证据或者调工具。

系统直答真正执行时，`streamSystemResponse(...)` 会优先选择节点自己的 `promptTemplate`；如果节点没配置模板，就回退到默认的 `answer-chat-system.st`。然后它会按固定顺序把 system prompt、历史消息和当前问题拼成消息列表，再直接交给 `llmService.streamChat(...)`。这里没有检索证据参与，所以它也不需要像 RAG 那样去等一大堆上下文返回，路径非常短。

这一阶段的关键方法主要有三个：

1. `intentResolver.isSystemOnly(...)` 负责判定是不是纯系统问题。
2. `promptTemplateLoader.load(...)` 负责在没有自定义模板时加载默认系统对话模板。
3. `streamSystemResponse(...)` 负责把模板、历史和当前问题组装成最终消息并流式输出。

### 2. 阶段 6：多通道检索

如果不是系统直答，Pipeline 就会进入多通道检索阶段。这里真正的核心不是“把所有库都搜一遍”，而是把 KB 和 MCP 两条完全不同的证据链拆开处理，再把结果重新收口。入口方法是 `RetrievalEngine.retrieve(...)`，它接收的是已经分类好的 `subIntents`，不会重新理解问题本身，只负责把这些子问题变成真正可执行的检索任务。

`RetrievalEngine` 内部会先为每个子问题构建 `SubQuestionContext`。这个过程中会用 `NodeScoreFilters.kb(...)` 和 `NodeScoreFilters.mcp(...)` 把 KB 意图和 MCP 意图拆出来，然后分别走不同的路径。KB 路径会调用 `retrieveAndRerank(...)`，内部再通过 `multiChannelRetrievalEngine.retrieveKnowledgeChannels(...)` 组织多通道知识检索；MCP 路径则会走 `executeMcpAndMerge(...)`，把用户问题变成工具参数后执行真实工具调用。最后两条链路得到的上下文，再被 `DefaultContextFormatter` 合并成一份结构化 `RetrievalContext`。

KB 方向里面还有一层非常关键的分流：`IntentDirectedSearchChannel` 和 `VectorGlobalSearchChannel`。前者是定向检索，只有真的识别出了 KB 意图才启用，而且会按 `collectionName` 去对应知识库定点搜索；后者是全局补底，主要在意图不够准或者置信度太低时打开，用来防止“目标库都选错”。两个通道跑完以后，还会经过 `DeduplicationPostProcessor` 做去重，再经过 `RerankPostProcessor` 做重排，最后只把真正值得给模型看的片段留下。

MCP 方向的逻辑则更像“查数据接口”。`executeMcpAndMerge(...)` 会先把对应的 MCP 意图筛出来，再调用 `executeMcpTools(...)` 并行执行各个工具。每个工具真正请求前，`LLMMCPParameterExtractor` 会根据 `MCPTool` 的定义和用户问题抽取参数；`buildMcpRequest(...)` 会把 toolId、问题和参数封装成标准请求；`executeSingleMcpTool(...)` 则负责找具体执行器并跑真正的工具逻辑。成功返回后，再由 `formatMcpContext(...)` 把结果整理成适合 Prompt 复用的动态数据块。

这一阶段最终得到的不是零散列表，而是统一的 `RetrievalContext`，里面同时保存 `kbContext`、`mcpContext` 和 `intentChunks`。这样做的好处是，后面组装 Prompt 时只要认这一份结构化结果，不需要再回头区分哪些是文档证据、哪些是工具数据。

### 3. 阶段 7：空结果兜底

检索完之后，Pipeline 会第一时间看 `retrievalCtx.isEmpty()`。如果 KB 和 MCP 两边都没有拿到任何可用上下文，那就说明这一轮已经没有继续往下生成的依据了。这时候系统不会把一份空上下文硬塞给大模型，而是直接通过 SSE 发回兜底信息，告诉用户当前没有相关内容。

`handleEmptyRetrieval(...)` 在这里做的不是补搜，而是止损。它把“没找到”这件事显式暴露出来，避免模型在没有证据的情况下继续胡乱发挥。这个设计的关键点在于，它不是异常中断，而是一个正常的短路分支：前端会收到完整的结束信号，但不会拿到一段建立在空地基上的答案。

### 4. 阶段 8：Prompt 组装与流式生成

只有前面三段都没有短路，系统才会进入最终生成阶段。`streamRagResponse(...)` 先把 KB 意图和 MCP 意图合并成一个 `IntentGroup`，再把当前问题、历史记忆、KB 上下文、MCP 上下文和意图片段一起封装到 `PromptContext` 里。到了这一步，系统已经不再是在“找资料”，而是在“准备如何让模型基于资料回答”。

真正组装消息的是 `RAGPromptService.buildStructuredMessages(...)`。它会先决定场景是 `KB_ONLY`、`MCP_ONLY` 还是 `MIXED`，然后按场景选择不同模板。消息顺序也很固定：先放 system prompt，再放证据块，再放历史消息，最后放当前问题；如果是多子问题场景，还会把子问题显式编号后再交给模型。这样做的目的是压低串答和漏答的概率，让模型知道自己要按哪一层证据作答。

最终模型调用由 `llmService.streamChat(...)` 完成，输出过程是流式的，不是一次性返回。`StreamChatEventHandler` 一边把增量内容切片推给前端，一边在结束时把完整回答写回会话记忆，形成下一轮可直接复用的上下文。也就是说，生成和落库不是两条独立链路，而是同一个流式处理器的前后两步。

### 5. 这四段连起来的意义

1. 系统直答负责把明显不用检索的问题提早放行。
2. 多通道检索负责把真正需要证据的问题找对、找全、找稳。
3. 空结果兜底负责在没有证据时及时止损。
4. Prompt 组装与流式生成负责把证据变成最终可用答案，并把答案回写成下一轮记忆。

### 6. 一句话总结

这一章的主线就是先判断能不能直答，不能就依次进入 KB/MCP 检索、空结果兜底和 Prompt 组装，最后把证据流式送回前端。

## 五、大模型没有记忆多轮对话怎么做到不失忆？

这一章聚焦“记忆系统本身”。大模型每次调用都是一次独立请求，它不会天然记住上一轮说过什么。所谓“不失忆”，其实不是模型自己长了记忆，而是后端把旧对话整理后，重新注入到了下一轮 Prompt 里。

![第三章-并行加载时序图](D:/develop/知识星球学习/ragent总结图/第二章-并行加载时序图.svg)

### 1. 记忆系统到底在解决什么问题

1. 第一类问题是代词和省略。用户说“它呢”“那个规则呢”，系统得知道“它”指的是前面哪件事。
2. 第二类问题是长期约束。比如用户前面已经说过预算、时间、系统版本，后面再追问时这些约束不能凭空丢掉。
3. 第三类问题是上下文连续性。用户觉得自己是在“继续聊同一个问题”，系统也要尽量给出这种体验。
4. 所以记忆系统的目标不是保存所有历史细节，而是让后续轮次还能拿到“够用的历史信息”。

### 2. 为什么拆成三层结构

![第三章-记忆系统三层结构](D:/develop/知识星球学习/ragent总结图/第二章-记忆系统三层结构.png)

1. 最外层是门面层，也就是 `ConversationMemoryService`，统一对外提供 `load`、`append`、`loadAndAppend`。
2. 中间层是持久化层，也就是 `ConversationMemoryStore`，负责消息怎么查、怎么写。
3. 另一条并列能力是摘要层，也就是 `ConversationMemorySummaryService`，负责摘要怎么生成、怎么读取、怎么装饰。
4. 这样拆的核心原因是解耦。换存储方案不影响压缩逻辑，换摘要策略也不影响消息落库方式。
5. 比如将来要从 PostgreSQL 直读扩展成“Redis 缓存 + PostgreSQL 回源”，只要新写一个 `ConversationMemoryStore` 实现，门面层和 Pipeline 可以一行不动。
6. 同理，将来把摘要从“整段 LLM 压缩”换成“增量式压缩”，也只需要替换摘要服务实现，不用改存储层。
7. 对 Pipeline 来说，它只关心最终拿到的是 `List<ChatMessage>`，不关心这份列表背后到底来自 PostgreSQL、Redis 还是摘要拼接。

### 3. `load(...)` 这段代码到底在做什么

1. 它先记录开始时间，方便打日志观测一次记忆加载总共花了多久。
2. 然后分别用 `CompletableFuture.supplyAsync(...)` 并行启动“加载摘要”和“加载历史”两个任务。
3. `CompletableFuture.allOf(...)` 用来等这两个任务都结束。
4. 两边都完成后，再 `join()` 拿到结果：一份摘要消息、一个历史消息列表。
5. 最后调用 `attachSummary(summary, history)` 合并成最终要返回的上下文。
6. 整个过程包在 `try-catch` 里，一旦并行任务、合并或日志阶段有异常，就统一记录错误并返回空列表。
7. 这段代码的设计重点，不是“并行很酷”，而是让记忆故障退化成“本轮没有上下文”，而不是整条问答失败。

### 4. 这里的降级策略到底是什么

1. 摘要路径降级成 `null`。意思是摘要是增强项，丢了它还能靠最近几轮原文继续答。
2. 历史路径降级成空列表。意思是历史读取失败时，尽量别把异常往整条主链路外扩。
3. 顶层 `load(...)` 还有一个总兜底，保证前面局部没兜住的异常最终也只会退化成空记忆。
4. 这三层降级叠起来，目标都一样：稳定优先。

### 5. 加载摘要和历史时，会不会再调一次 LLM

1. 不会。
2. `loadSummaryWithFallback(...)` 只是去摘要表读“之前已经生成并落库”的最新摘要。
3. `loadHistoryWithFallback(...)` 只是去消息表读最近几轮历史消息。
4. 真正调用 LLM 生成摘要，只发生在压缩链路里，也就是 `compressIfNeeded(...) -> doCompressIfNeeded(...)` 那条后台路径。
5. 所以“加载记忆”和“生成摘要”在时序上是两回事。

### 6. 滑动窗口到底体现在哪

1. 不是在 `load(...)` 这层体现，而是在 `JdbcConversationMemoryStore.loadHistory(...)` 里体现。
2. 它先按 `historyKeepTurns * 2` 算窗口大小，只取最近几轮 `user + assistant` 消息。
3. 数据库里先按倒序取最新 `N` 条，再在内存里反转成正序。
4. 然后通过 `map(this::toChatMessage)` 统一消息结构，再 `filter(this::isHistoryMessage)` 过滤掉不适合参与历史注入的记录。
5. 最后 `normalizeHistory(...)` 负责修窗口边界，保证历史切片尽量以 `user` 消息开头。
6. 这就是“窗口从尾部截，但喂给模型时仍保持正常对话顺序”的完整实现思路。

### 7. `listMessages(...)` 这个接口除了查消息，还做了什么

1. 它先校验 `conversationId` 和 `userId` 是否为空。
2. 再先查会话本身是否存在，不存在就直接返回空列表。
3. 接着按 `createTime` 升序或降序查消息，支持 `limit`。
4. 如果是降序查，查回来后会 `Collections.reverse(records)`，统一还原成正常时间顺序。
5. 然后它会额外挑出所有 `assistant` 消息 ID，去 `feedbackService.getUserVotes(userId, assistantMessageIds)` 批量查用户对这些回复的点赞/点踩反馈。
6. 最后把数据库记录组装成 `ConversationMessageVO` 返回给前端。
7. 之所以只给 `assistant` 消息补反馈，是因为用户反馈的对象就是系统给出的回答；前端要知道某条回答当前用户已经赞过、踩过还是没操作过。

### 8. 摘要和历史是怎么合并的

1. `attachSummary(summary, messages)` 先看历史是否为空；历史为空时直接返回空列表。
2. 如果历史有、摘要没有，就直接返回历史。
3. 如果摘要也有，就先把摘要装饰成 `SYSTEM` 消息放在第一个位置。
4. 后面再原样拼上历史消息列表。
5. 所以摘要不是和历史做“文本拼接”，而是作为一条真正的系统消息插进消息数组最前面。

### 9. 记忆注入 Prompt 的完整顺序

1. 先注入摘要，让模型先知道“长期背景和约束”。
2. 再注入最近几轮原文，让模型拿到细节和最新互动脉络。
3. 最后再单独拼当前用户问题，避免当前问题在历史里出现两次。
4. 这个顺序决定了模型看到上下文时的阅读方式：先全局，再近期，最后当前。

### 10. 一句话总结

这一章的主线就是把历史消息、长期摘要和当前问题按固定顺序重新组装进下一轮 Prompt，让模型拿到的不是“自己记住的上下文”，而是后端替它整理好的可复用记忆。

## 六、聊满 50 轮，Token 爆了，记忆该压缩还是该删？

这一章讲的是长对话里的“记忆保鲜”问题。会话越长，原文消息越多，Prompt 的 Token 预算越容易爆。系统既不能无限保留所有原文，也不能把早期历史直接删光，所以最终选择的是“近期原文 + 早期摘要”的混合策略。

### 1. 为什么不能一直保留全部原文

1. 上下文窗口不是无限的，历史越长，留给当前问题和检索片段的 Token 越少。
2. 即使模型窗口还装得下，历史过长也会引入噪音，让真正关键的近期信息被稀释。
3. 所以系统必须主动做裁剪，而不是等窗口爆掉再临时处理。

### 2. 为什么又不能简单直接删掉

1. 早期对话里经常藏着长期约束，比如预算、系统版本、项目背景、之前已经试过哪些方案。
2. 这些信息虽然不需要保留每句原话，但如果整段删掉，后面继续追问时系统就会像失忆一样。
3. 所以删除不是目标，浓缩才是目标。

### 3. 什么时候触发摘要压缩

1. 压缩不是每来一条消息就做。
2. 只有 `ASSISTANT` 消息写入后，才会触发 `compressIfNeeded(...)` 检查。
3. 原因很简单：`assistant` 到达意味着一轮完整对话闭环了，这时候压缩才不会少半轮语义。
4. 压缩任务通过 `CompletableFuture.runAsync(...)` 丢到专用线程池执行，不阻塞主请求响应。

### 4. 压缩范围是怎么界定的

![第四章-水位线与压缩演进](D:/develop/知识星球学习/ragent总结图/第四章-水位线与压缩演进.svg)

1. 系统不会每次都把“全量历史”重新拿给模型压缩。
2. 它会先查最新摘要，看上一次摘要已经覆盖到哪条消息，也就是 `lastMessageId` 水位线。
3. 然后再根据当前滑动窗口边界算出新的 `cutoffId`。
4. 本次真正要压缩的，只是“上次摘要之后，到这次窗口边界之前”的那一段旧消息。
5. 这样做的好处是增量压缩，不重复处理已经被摘要覆盖过的消息。

### 5. 为什么要有分布式锁和阈值

1. 同一会话的摘要压缩是有共享状态的，多个后台任务同时做会互相踩水位线。
2. 所以系统会基于 `conversationId + userId` 抢一把会话级分布式锁。
3. 抢不到就直接退出，让当前这次后台任务放弃。
4. 抢到锁之后，还要再看 `summaryStartTurns` 是否达到阈值，不到阈值就不压。
5. 这两层保护分别解决“并发重复压缩”和“对话太短没必要压缩”。

### 6. 生成摘要时，到底给 LLM 传了什么

1. 第一条是 `SYSTEM` Prompt，写清楚摘要角色、长度约束、输出格式和保留原则。
2. 第二条在已有旧摘要时会出现，是一条 `ASSISTANT` 消息，内容是“历史摘要，仅用于合并去重，不得作为新增事实来源”。
3. 然后才是这次待压缩的原始历史消息，按原始顺序喂进去。
4. 最后一条是 `USER` 指令，明确要求合并以上内容、去重后输出一行新摘要。
5. 所以摘要链路本质上也是一套专门的 Prompt 工程，而不是简单把历史拼成一段长文本。

### 7. 这些核心约束各自想控制什么

1. 长度限制控制 Token 预算。摘要最终也是要注入问答 Prompt 的，不能无限长。
2. 话题颗粒度控制信息密度。模型如果只写“咨询了人事制度”，信息量太低，后面几乎不能用。
3. 记录范围控制摘要职责。系统要保留“聊过什么、当前是什么状态、用户有什么约束”，而不是把完整答案再抄一遍。
4. 单行输出控制可注入性。摘要最终要作为一条消息插进上下文，越规整越容易稳定复用。

### 8. `话题+状态`、`关键约束`、`关键词` 该怎么区分

1. `话题+状态` 是最核心的信息，表示“聊了什么”和“聊到哪一步了”。例如“咨询了年假天数计算规则（已解答）”。
2. `关键约束` 是会影响后续回答方向的条件，比如预算、时间、地区、系统版本、渠道限制。
3. `关键词` 只是辅助检索和定位的残余标记，信息价值最低。
4. 所以字数不够时，优先保留 `话题+状态`，其次保留 `关键约束`，最后才是 `关键词`。
5. 这个优先级的本质是：先保留能支撑继续对话的骨架，再保留帮助收窄答案范围的条件，最后才是零散标签。

### 9. 状态标注规范到底放在哪里

1. `已解答`、`当时无记录`、`部分解答`、`待确认` 这些状态，不是数据库里的独立字段。
2. 它们体现在摘要文本本身，是被摘要 Prompt 约束出来的一套输出规范。
3. 也就是说，摘要表里存的是“一整段摘要内容”，状态信息是摘要内容里的语义片段，不是单独的列。
4. `当时无记录` 这个“当时”尤其重要。它是在提醒后续模型：上次没查到，不代表现在知识库也没有，当前轮仍然应该继续检索。

### 10. 一句话总结

这一章的主线就是不直接删历史，而是用滑动窗口 + 增量摘要 + 水位线压缩，把长对话的 Token 预算和记忆连续性一起保住。

## 七、用户说的话 ≠ 该搜的词

这一章讲的是查询改写层。用户说的话适合聊天理解，不一定适合向量检索和关键词检索。系统需要先把“人话”改造成“检索话”，必要时还要顺手拆成多个子问题，才能让后面的意图识别和检索更稳定。

### 1. 为什么用户原话不能直接拿去搜

1. 多轮对话里，用户经常说“它”“这个”“顺便再问一句”。
2. 聊天模型能靠上下文理解这些代词，但检索引擎不会自动做指代消解。
3. 如果直接拿“那它的保修期呢”去搜，检索质量往往会明显下降。
4. 所以改写层的核心任务，是把依赖上下文的人类表达转成独立、明确、可检索的查询。

### 2. 为什么不仅要改写，还要拆分子问题

1. 一句话里可能同时问两个完全不同的方向。
2. 只做改写不做拆分，后面的意图识别可能只命中其中一个方向。
3. 拆成多个子问题后，每个子问题都能独立做意图分类、检索和路由。
4. 所以这里的设计目标是双重的：改写提升检索精度，拆分提升意图覆盖率。

### 3. 术语归一化这层到底在做什么

1. `QueryTermMappingService.normalize(String text)` 会先做一层纯规则的术语清洗。
2. 它会优先从 Redis 里取映射规则；缓存命中就直接用。
3. 缓存未命中时，再去数据库表 `t_query_term_mapping` 读取所有 `enabled=1` 的规则。
4. 读出来后会按“优先级降序 + 源词长度降序”排序，目的是先匹配更重要、也更长的词，减少短词误伤。
5. 然后逐条调用 `QueryTermMappingUtil.applyMapping(...)` 把文本里的别名、简称、俗称替换成系统内部更标准的目标词。
6. 查库拿到新规则后，还会 `saveMappingsToCache(dbList)` 回填 Redis。
7. 这里的“回填”不是多做了一步花活，而是典型的 Cache-Aside：这次查库顺手把最新规则写回缓存，下次就不用再打数据库。

### 4. 映射规则现在放在哪里

1. 持久化源头是数据库表 `t_query_term_mapping`。
2. 运行时优先从 Redis 取一份规则缓存。
3. Redis 没命中时再回源数据库，并把结果重新写回 Redis。
4. 所以“规则存在哪里”的准确答案是：长期存数据库，热点读取走 Redis。

### 5. 如果要新增一条映射规则，最终该落什么数据

1. 最关键的字段是 `sourceTerm` 和 `targetTerm`，也就是“用户怎么说”和“系统最终按什么搜”。
2. 还要配置 `matchType`，决定是精确替换、前缀匹配还是其他匹配方式。
3. `priority` 用来处理规则冲突，数值越重要的规则越应该先参与。
4. `enabled` 控制规则是否生效。
5. `domain` 和 `remark` 则适合做业务域隔离和维护备注。
6. 所以不管你是走后台管理页还是直接入库，最终都要落到 `t_query_term_mapping` 这张表。

### 6. `rewriteWithSplit` 的完整链路

1. Pipeline 在阶段 2 调用的是最完整的方法：`rewriteWithSplit(question, history)`。
2. 第一步不是调 LLM，而是先做术语归一化。
3. 第二步看开关。如果 `rag.query-rewrite.enabled=false`，就直接走规则拆分，不调用 LLM。
4. 第三步如果开关开启，就把改写 Prompt、最近一两轮历史、归一化后的当前问题拼成一组消息。
5. 这里的 `messages.add(ChatMessage.system(systemPrompt))`，本质上是把渲染好的整段 Prompt 模板文本作为一条 `SYSTEM` 消息塞进去，不是把某个文件原样上传。
6. 然后通过一次 `llmService.chat(...)` 同时拿到两个结果：改写后的主问题和子问题列表。
7. 调用成功后还要继续过 JSON 清洗和解析；只有结构化结果合法，才算真正成功。
8. 如果 LLM 调用异常，或者 JSON 解析失败，就统一降级成 `new RewriteResult(normalizedQuestion, List.of(normalizedQuestion))`。
9. 所以这里说的“唯一子问题”，不是原始用户原话，而是“术语归一化之后的那个单一检索问题”。

![第五章-改写兜底三层链路](D:/develop/知识星球学习/ragent总结图/第五章-改写兜底三层链路.svg)

### 7. 为什么接口要设计成三层回退

1. `QueryRewriteService` 先定义了最基础的 `rewrite(String userQuestion)`。
2. 然后提供默认实现的 `rewriteWithSplit(String userQuestion)`。
3. 再提供带历史的 `rewriteWithSplit(String userQuestion, List<ChatMessage> history)`。
4. 这意味着将来如果有一个非常简单的规则改写器，只实现 `rewrite()` 也能工作。
5. 因为上层即使调用最完整的 `rewriteWithSplit(question, history)`，也会通过 default 实现一路回退到 `rewrite()`，不会因为你没实现更复杂的方法而直接报错。
6. 当前主流程里，`MultiQuestionRewriteService` 直接覆盖了最完整版本，用一次 LLM 调用同时完成改写和拆分。

### 8. 为什么改写只看最近一两轮历史

1. 改写层主要解决的是指代消解、轻度上下文补全和复合问题识别。
2. 这类任务通常不需要很长历史，最近一两轮已经够判断“它”“这个”到底指什么。
3. 给太长历史只会多耗 Token，还可能引入噪音，让模型过度改写。
4. 所以这里追求的不是“记忆越多越好”，而是“只拿改写真正需要的最小上下文”。

### 9. 为什么改写失败不能拖垮主流程

1. 查询改写是增强项，不是硬依赖。
2. 开关关掉了，系统还能继续跑。
3. LLM 调用失败了，系统还能继续跑。
4. JSON 解析失败了，系统还能继续跑。
5. 最坏情况只是退化成“直接拿归一化后的问题去搜”，或者再差一点，拿原问题去搜。
6. 精度可能下降，但整条 RAG 主链路不能因为改写层失败而不可用。

### 10. 一句话总结

这一章的主线就是先把用户原话做术语归一化，再在必要时做改写与拆分，最后用 JSON 解析和三级兜底把“人话”转成真正可检索的问题。

## 八、四分类撑不住 20 个知识库为什么要设计意图树

这一章讲的是意图路由为什么不能停留在“知识库、工具、系统直答、歧义引导”这种平面四分类上。四分类只能回答“这类问题大概要走哪条大路”，却回答不了“具体该去哪个知识库、哪个 MCP 工具、哪个系统节点”。

### 1. 为什么平面四分类到后面一定不够用

1. 当系统里只有一个知识库时，分类成“知识库问题”已经够了，因为分类完直接搜这一个库就行。
2. 但知识源一旦扩展到十几个、几十个，光知道“这是知识库类问题”没有意义。
3. 真正关键的问题变成了：该去哪个 Collection、哪个 MCP 工具、哪个系统直答节点。
4. 所以四分类解决的是“属于哪条大路”，不是“落到哪个具体站点”。

### 2. 为什么不能简单粗暴地全库都搜

1. 第一个问题是成本高。20 个知识库各取 Top-K，再统一 rerank，候选量和延迟都会明显上涨。
2. 第二个问题是噪音大。不同知识库的 chunk 全混在一起，会让不相关但表面相似的内容挤进前排。
3. 第三个问题是答案容易漂。检索范围越大，模型后面越容易被无关上下文带偏。
4. 所以系统需要的不是“先全搜再慢慢挑”，而是“先把搜索范围缩小到最可能的那个子树”。

### 3. 意图树的本质：从大类到细类逐步收窄

1. 这套系统把路由结构组织成一棵树，典型层级是 `DOMAIN -> CATEGORY -> TOPIC`。
2. `DOMAIN` 解决“这是哪一大片业务域”。
3. `CATEGORY` 解决“这个业务域里的哪一类问题”。
4. `TOPIC` 解决“最后具体落到哪个知识点、哪个工具或哪个系统节点”。
5. 这和数据库里的表设计没有直接关系，它首先是一个语义路由结构。

![第六章-意图树整体结构](D:/develop/知识星球学习/ragent总结图/第六章-意图树整体结构.png)

### 4. 为什么只让叶子节点参与最终匹配

1. 在运行时，真正喂给 LLM 打分的不是整棵树，而是所有叶子节点。
2. `IntentNode.isLeaf()` 的实现也很直接，只看 `children` 是否为空，不看 `level`。
3. 这意味着一个没有子节点的 `CATEGORY` 也能成为叶子，不一定非得是 `TOPIC` 才能落地。
4. 中间节点的职责主要是组织结构和帮助收窄范围，不一定直接执行检索或调工具。
5. 只有叶子节点才真正对应“可执行目标”，比如具体的 KB Collection、MCP 工具或系统直答节点。

### 5. 为什么要把 `KB / MCP / SYSTEM` 统一挂在一棵树里

1. 用户问题最终要去的目标，不止可能是知识库。
2. 有的问题应该搜 KB，有的问题应该调 MCP 工具拿实时数据，有的问题压根就是系统直答。
3. 所以这棵树不是“知识库目录树”，而是“所有可路由目标的统一语义树”。
4. 在 `IntentNode` 上，这种差异由 `kind` 来表达：`KB`、`MCP`、`SYSTEM`。
5. 这样上层意图识别只做一件事：找到最合适的叶子节点。至于后面是检索、调工具还是系统直答，由叶子节点自己的 `kind` 决定。

### 6. 一个 `IntentNode` 上到底装了哪些信息

1. 识别层信息：`id`、`name`、`level`、`parentId`、`fullPath`。
2. 语义匹配信息：`description`、`examples`。
3. 路由信息：`kind`、`collectionName`、`mcpToolId`、`topK`。
4. 生成控制信息：`promptSnippet`、`promptTemplate`、`paramPromptTemplate`。
5. 这说明节点不是一个单纯的“标签”，而是同时携带了“怎么匹配、匹配后去哪里、回答时怎么约束”的复合配置。

### 7. 数据库里为什么不是直接存树

1. 持久化时，系统把节点平铺存到 `t_intent_node` 表里。
2. 表里保存的是 `intentCode`、`parentCode`、`level`、`kind`、`collectionName`、`mcpToolId`、Prompt 配置等字段。
3. 这样做的原因很工程化：后台 CRUD 容易做，SQL 好查，单个节点更新也简单。
4. 运行时再由服务层把平铺记录重新组装成树。
5. `DefaultIntentClassifier` 会先把节点全部加载出来，再扁平化、筛叶子节点，最后用叶子节点生成分类 Prompt。

### 8. Redis 缓存起的是什么作用

1. 意图树结构相对稳定，但读取频繁，非常适合缓存。
2. 当前缓存键是 `ragent:intent:tree`。
3. 运行时会先尝试从 Redis 直接拿整棵树。
4. Redis 没有时，再回源数据库重组，并把整棵树重新写回 Redis。
5. 这也是一套标准的 Cache-Aside 思路，只不过缓存对象不是单条记录，而是整棵树。

这张图对应的就是“意图树加载 + 缓存回填 + 运行时整理”的完整流程：

![第六章-意图树加载流程](D:/develop/知识星球学习/ragent总结图/iShot_2026-04-23_16.38.61.svg)

把图里的每一步和代码对应起来，大致就是下面这条链路：

1. **读 Redis 缓存**：`DefaultIntentClassifier.loadIntentTreeData()` 先调 `intentTreeCacheManager.getIntentTreeFromCache()`，尝试直接拿 `ragent:intent:tree` 这份整树快照。
2. **缓存命中**：如果 Redis 里已经有树，就不再查库，直接进入后面的运行时整理阶段。
3. **缓存未命中，查数据库**：如果 Redis 没有，就走 `loadIntentTreeFromDB()`，从 `t_intent_node` 里查出所有启用节点。
4. **DO -> IntentNode 转换**：数据库里的 `IntentNodeDO` 会先转成内存对象 `IntentNode`，同时把 `intentCode -> id`、`parentCode -> parentId` 这类持久化字段映射成运行时字段。
5. **根据 parentId 组装树**：服务层按父子关系把平铺节点重新挂回树结构；找不到父节点的，就当作根节点。
6. **递归补 fullPath**：树组好以后，会继续把每个节点的全路径补齐，方便后面做语义匹配和日志展示。
7. **写回 Redis 缓存**：如果这次是从数据库重建出来的树，就调用 `intentTreeCacheManager.saveIntentTreeToCache(roots)`，把整棵树序列化成 JSON，缓存 7 天。
8. **flatten 扁平化所有节点**：无论是从 Redis 直接拿到的树，还是刚从数据库重建好的树，后面都会统一走 `flatten(roots)`，把整棵树拍平成 `allNodes` 列表。
9. **过滤叶子节点**：再从 `allNodes` 里筛出 `leafNodes`，也就是真正会参与 LLM 打分的最终候选节点。
10. **构建 id -> Node 查找表**：同时再生成一份 `id2Node` 映射，方便后面根据 LLM 返回的 `id` 迅速定位到具体节点对象。
11. **返回 IntentTreeData**：最后把 `allNodes`、`leafNodes`、`id2Node` 一起打包成 `IntentTreeData` 返回给分类器，后面构造 Prompt 和解析 LLM 返回值都会直接用这三份数据。

所以这张图最关键的一点不是“Redis 命中就结束了”，而是：**Redis 解决的是整棵树的读取成本，命中之后仍然要继续做 flatten、筛叶子和建索引，才能变成 LLM 分类阶段真正可直接消费的数据结构。**

### 9. 为什么后台维护时要强制子树一致

1. 树结构不是孤立节点集合，父节点和子节点状态必须一致。
2. 如果你停用了父节点，但叶子节点还启用着，运行时仍可能把问题路由到这些叶子上，结构就会出现逻辑断裂。
3. 所以后台在批量停用、批量删除时，会检查你是不是把整棵子树一起选上了。
4. 如果只选父节点、不选已启用的子节点，操作会被拒绝。
5. 同时，每次 create、update、delete、batch 操作后，都会清掉意图树 Redis 缓存，保证下次读取拿到的是新结构。

### 10. `IntentTreeFactory` 和数据库各扮演什么角色

1. 项目里保留了一个 `IntentTreeFactory`，它更像是初始化模板来源。
2. 新环境可以通过它生成一套默认树，再写入 `t_intent_node`。
3. 但正式运行后，真正的事实来源是数据库，而不是 Factory 里的硬编码结构。
4. 也就是说，Factory 负责“冷启动”，数据库负责“长期演进”。

### 11. 一句话总结

这一章的主线就是把四分类升级成树形路由，让 KB、MCP、SYSTEM 都挂在同一棵意图树上，再通过缓存、叶子节点和运行时重建完成精细分流。

## 九、怎么让大模型同时看 30 个意图节点打分？

### 1. 先搞清楚这个问题在解决什么

1. 到了意图识别这一步，系统其实已经拿到了整棵意图树，也已经筛出了所有叶子节点。
2. 但“拿到叶子节点”不等于“模型就能直接判断哪个最匹配”。
3. 对 LLM 来说，这些节点必须先被整理成一份结构清楚、长度可控、语义够全的候选列表。
4. 所以这一章真正讲的，不是“模型为什么会打分”，而是“后端怎么把 30 个候选节点整理成一份 LLM 看得懂、也不容易看乱的分类清单”。
5. 换句话说，这一步是在把树结构数据，翻译成一份适合大模型做分类判断的 Prompt 输入。

这张图对应的就是“候选叶子节点准备好后，如何拼 Prompt、调模型、清洗结果并拿回候选意图”的完整链路：

![第八章-意图节点打分链路](D:/develop/知识星球学习/ragent总结图/第八章-意图节点打分链路.svg)

### 2. 整体链路先看一遍

1. `IntentResolver.resolve(...)` 先拿到当前子问题。
2. 然后进入 `classifyIntents(...)`，开始做单个子问题的意图分类。
3. `DefaultIntentClassifier` 会先加载意图树数据，拿到 `allNodes`、`leafNodes` 和 `id2Node`。
4. 真正参与这一轮打分的，是 `leafNodes`，也就是所有可直接落地执行的叶子节点。
5. 接着 `buildPrompt(leafNodes)` 会把这些叶子节点序列化成一段紧凑文本，再填进分类 Prompt 模板。
6. 后端随后用“系统消息 + 当前问题”两条消息调用 LLM，让模型返回 JSON 格式的候选意图及分数。
7. 模型结果回来后，不会直接信，而是先清洗 Markdown 代码块、再解析 JSON、再按分数阈值和数量限制做过滤。
8. 最后才把真正保留下来的节点，交回上层继续往后走检索、工具调用或系统直答链路。

### 3. `buildPrompt()` 到底在做什么

1. 这个方法的核心任务，就是把每个叶子节点整理成一个统一的小文本块。
2. 每个节点至少会带上 `id`、`path`、`description`、`type`、`examples` 这些字段。
3. 如果节点是 `MCP` 类型，还会额外把 `toolId` 也带上，方便模型理解这是工具调用节点，不是知识库节点。
4. 最终得到的不是 JSON，而是一串连续的 `key=value` 风格文本。
5. 所有节点拼完以后，再作为 `intent_list` 填进 `intent-classifier.st` 这个 Prompt 模板。

它整理出来的大概就是这种信息结构：

1. `id`：给模型一个唯一标识，后面返回结果时也必须靠它回连到具体节点。
2. `path`：告诉模型这个节点在整棵树里的位置，比如它属于物流、售后还是系统交互。
3. `description`：这是语义匹配的主依据，说明这个节点到底覆盖什么问题。
4. `type`：告诉模型命中后会走 KB、MCP 还是 SYSTEM。
5. `examples`：相当于给模型补一层轻量 few-shot，让它知道这类节点平时长什么问题。

### 4. 为什么这里不用 JSON，而要用 `key=value`

1. 第一是省 Token。节点一多，JSON 里的花括号、引号、逗号都会变成额外成本。
2. 第二是可读性够强。对分类任务来说，`id=...`、`path=...` 这种格式已经足够清楚。
3. 第三是方便把很多节点压缩到一个 Prompt 里，不至于把结构开销放大。
4. `examples` 也被压成一行，用 `/` 分隔，而不是一个示例占一行，本质上也是在做长度控制。
5. 所以这里的设计目标不是“最标准的数据格式”，而是“在模型可读和 Prompt 成本之间取一个更合适的平衡点”。

### 5. 模型真正看到的输入，不止节点列表

1. 节点列表只是材料，真正起判断作用的是完整的分类 Prompt。
2. 这份 Prompt 里除了 `intent_list`，还会告诉模型它的角色是什么、每个字段代表什么、应该怎么判断、怎么打分、最后必须按什么 JSON 格式输出。
3. 也就是说，后端并不是把 30 个节点一股脑扔给模型说“你自己猜”，而是给了它一套很明确的判题规则。
4. 到真正调用 LLM 时，消息通常很克制，只有两条。
5. 第一条是 `system` 消息，里面装的是渲染好的分类 Prompt；第二条是 `user` 消息，也就是当前正在分类的那个问题。

这一步有一个很重要的边界：这里分类的对象，是当前这个子问题，而不是整段历史对话的全文重判。历史上下文如果有用，通常已经在上游改写阶段被折叠进当前问题表达里了；到了分类这一步，模型看的核心输入就是“这一个待分类的问题”。

### 6. Prompt 模板是怎么加载与渲染的

1. 模板路径不是写死在业务代码里的长字符串里，而是先定义成一个常量：`INTENT_CLASSIFIER_PROMPT_PATH = "prompt/intent-classifier.st"`。
2. 当 `buildPrompt(leafNodes)` 把所有叶子节点拼成 `sb.toString()` 之后，并不会自己手工去做字符串替换，而是调用 `promptTemplateLoader.render(...)`。
3. `render(...)` 会先执行 `load(path)`，把模板内容读出来；如果这个模板之前已经加载过，就直接从内存缓存里拿，不会每次都重新读文件。
4. 当前项目的 `PromptTemplateLoader` 用的是一个 `ConcurrentHashMap<String, String>` 做缓存，核心逻辑就是 `cache.computeIfAbsent(path, this::readResource)`。
5. 这意味着它采用的是懒加载策略：不是项目启动时一次性把所有 Prompt 全读进来，而是谁第一次用到哪个模板，才第一次去读哪个模板。

真正的读取动作发生在 `readResource(path)`：

1. 它会先把 `prompt/intent-classifier.st` 这种路径补成 `classpath:prompt/intent-classifier.st`。
2. 然后通过 Spring 的 `ResourceLoader` 去类路径下找这个资源文件。
3. 找到之后按 UTF-8 读成一个完整字符串。
4. 如果文件不存在，直接抛异常；如果读取失败，也会记录日志并抛异常。
5. 所以模板文件的事实来源，不是在数据库，也不在 Redis，而是在项目资源目录里的 `.st` 文件。

读到模板之后，`render(...)` 还会再做两步：

1. 第一步是 `fillSlots(template, slots)`，把模板里的占位符替换掉。对于意图分类来说，最关键的占位符就是 `{intent_list}`，会被替换成 `buildPrompt()` 刚刚拼出来的那一大段叶子节点列表。
2. 第二步是 `cleanupPrompt(filled)`，把替换之后可能出现的多余空行、空占位痕迹之类做一次清理，让最终 Prompt 更干净。

所以这一步可以理解成一个很清晰的四段式链路：

1. `buildPrompt()` 先准备动态数据，也就是叶子节点列表。
2. `PromptTemplateLoader.load()` 负责把静态模板文件从 `classpath` 读出来，并缓存起来。
3. `PromptTemplateLoader.render()` 再把动态数据填进模板槽位里。
4. 最后得到一份完整的 system prompt，再交给 LLM 做分类。

如果把它和前面那段节点序列化放在一起看，其实就是一句话：**`buildPrompt()` 负责造“题目材料”，Prompt 模板负责造“判题规则”，`render()` 负责把两者真正拼成一份完整提示词。**

### 7. Prompt 是怎么教模型打分的

1. 它不是只说一句“请选最相关节点”，而是把判断过程拆得比较细。
2. 第一层先区分两种问题：实体导向问题和主题导向问题。
3. 实体导向问题，要求模型更看重具体实体名、系统名、产品名、模块名这类强特征，不能只因为领域相近就乱配。
4. 主题导向问题，则允许模型更多参考 `path` 和 `description` 里的主题词、同义词和典型场景。
5. 这种拆法的目的，是同时解决两个相反的问题：既防止“过度联想乱命中”，也防止“没有精确实体就完全漏掉”。

继续往下，Prompt 还会再加三类约束：

1. 数量约束：默认只返回最核心的 1 个主意图，只有确实存在两个独立方向或明显歧义时，才放宽到多个。
2. 类目约束：用户如果已经明确说了“跨境物流”“退换货”这类方向，就不要轻易跨类目去选别的节点。
3. 空结果约束：如果所有候选都只是勉强沾边，宁可返回空，也不要硬凑一个弱相关答案。

### 8. 为什么默认只保留一个主意图

1. 因为在它前面，查询改写和子问题拆分已经先做过一轮清洗了。
2. 理想情况下，进入 `classifyIntents(...)` 的应该是一个比较干净的单子问题，而不是一大串混杂诉求。
3. 既然输入已经被拆细了，那这一层就应该收窄，而不是再把一堆候选都放出来。
4. 默认只保留一个主意图，本质上是在逼分类器做明确判断。
5. 这样后面的检索范围会更小，召回噪音也更少，最终答案更稳。

当然也留了少量例外：

1. 如果一个问题里确实还有两个独立诉求，允许返回两个候选。
2. 如果用户只说了一个模糊主题词，而且这个主题在多个类目下同名出现，也允许保留少量候选，供后面做引导澄清。
3. 但这个“放宽”仍然是受控的，不是让模型随便多选。

### 9. 为什么模型调用参数要故意调保守

1. 这一层做的是分类，不是创作。
2. 所以参数设置上，会更偏向稳定、一致、少发散。
3. 比如温度会压得比较低，`topP` 也会收得比较紧，同时关闭不必要的深度思考输出。
4. 这样做的目标，不是让模型“更聪明”，而是让它在同样的问题和同样的候选列表下，更容易给出稳定可复现的判断。
5. 对分类链路来说，稳定比华丽更重要。

### 10. 模型返回后，后端为什么还要再清洗一遍

1. 因为 LLM 即使被要求“只输出 JSON”，也不一定每次都老老实实。
2. 它可能外面包一层 Markdown 代码块，也可能返回一个对象再把真正结果包在 `results` 字段里。
3. 所以后端会先做一次响应清洗，把 ```json 这种围栏去掉，再尝试解析。
4. 解析后也不会盲信，每个结果还要继续校验：`id` 能不能在 `id2Node` 里找到、分数字段是否正常、结构是否完整。
5. 找不到节点、字段缺失、格式异常的项，都会被跳过，而不是强行吞下去。

这一步背后的思路很朴素：Prompt 约束解决的是“大多数时候怎么返回”，结果清洗解决的是“万一它没按规矩来怎么办”。

### 11. 打分结果回来后，为什么还要再过滤

1. 模型给分，只代表它的主观判断，不代表系统要把所有返回项全收下。
2. 后端通常还会再设一道最低分门槛，先过滤掉明显偏弱的候选。
3. 然后再按得分从高到低截断，只保留前几项。
4. 再往上层，还有一次总量封顶，避免多个子问题叠加后意图数失控。
5. 所以“LLM 打分”只是中间环节，真正进入后续检索链路的，是经过后端二次筛选后的结果。

### 12. 打分出来以后，怎么继续决定查哪个库、查多少条

1. `classifyIntents(...)` 给出来的只是“候选意图分数”，真正进入检索阶段时，还要把它映射成具体的 `collectionName` 和 `topK`。
2. `IntentDirectedSearchChannel` 会先看意图节点绑的是哪个知识库，再用这个节点的分数决定定向通道要不要启用；本篇里的 `rag.search.channels.intentDirected.minIntentScore=0.4` 是定向检索的激活门槛，和前面分类阶段的 `INTENT_MIN_SCORE=0.35` 不是同一个阈值。
3. 真正“查多少条”是两级决定的：子问题级先取该节点配置的 `topK`，没有配置就退回 `DEFAULT_TOP_K=10`；然后再乘通道倍率，定向检索 `topKMultiplier=2`，全局检索 `topKMultiplier=3`。
4. 所以这里的规则可以概括成一句话：**分数负责决定查不查，节点配置负责决定基数，通道倍率负责决定放大多少。**
5. 下面这张图把“意图分数 -> 检索库 -> 检索条数”的映射关系画得更直观：

![第九章-意图分数到检索参数映射](D:/develop/知识星球学习/ragent总结图/image-20260428144659767.png)

### 13. 一句话总结

这一章的主线就是先把叶子节点压成 LLM 可读的候选清单，再用低发散 Prompt 打分、结果清洗和阈值过滤，把分数映射成后续该查哪个库、查多少条。

## 十、三个子问题命中了八个意图，该保留哪几个

### 1. 这个问题为什么会出现

1. 到了这一步，系统前面其实已经做了不少收敛动作。
2. 查询改写已经把一句复杂问题拆成了多个子问题，单个子问题内部的意图分类也已经做过一次分数过滤和数量限制。
3. 但只控制“单个子问题内部”还不够，因为多个子问题一叠加，总意图数还是可能一下膨胀起来。
4. 比如三个子问题，每个子问题各保留 2 到 3 个候选，合起来就可能变成 8 个甚至 9 个意图。
5. 这时候如果把它们全丢给下游检索，延迟、成本和噪音都会一起上来。

所以这一章真正要解决的问题是：**多个子问题各自都有道理时，系统怎么在不饿死任何一个子问题的前提下，把总意图数压回一个可控范围。**

![第九章-总量封顶算法](D:/develop/知识星球学习/ragent总结图/第九章-总量封顶算法.svg)

### 2. 第一层控制只管“单题”，还不管“全局”

1. 在 `classifyIntents(question)` 里，系统已经先做过一轮单题过滤。
2. 第一道筛子是 `INTENT_MIN_SCORE`，分数太低的候选直接丢掉。
3. 第二道筛子是 `limit(MAX_INTENT_COUNT)`，限制单个子问题最多保留多少个意图。
4. 这一步解决的是“某一个子问题别一下带出太多弱相关候选”。
5. 但它没有解决“多个子问题加起来总共保留多少个”的问题。

也就是说：

1. 单题过滤控制的是局部噪音。
2. 总量封顶控制的是全局规模。
3. 这两层看起来都在“裁剪意图”，但面对的不是同一个问题。

### 3. 真正做全局裁剪的是 `capTotalIntents(...)`

1. `IntentResolver.resolve(...)` 在并行收齐所有 `SubQuestionIntent` 之后，不会直接把结果往下传。
2. 它还会额外走一次 `capTotalIntents(subIntents)`。
3. 这一步的目标很明确：限制这次请求里所有子问题加起来的意图总数，不超过 `MAX_INTENT_COUNT`。
4. 当前默认值是 3。
5. 所以这一步是在回答：如果现在一共有 8 个意图，但系统最多只想让 3 个进入后续链路，那最后留谁。

### 4. 为什么不能简单按全局分数截前 3

1. 因为这样很容易把某个子问题整个“饿死”。
2. 假设子问题 A 命中了两个高分意图，子问题 B 命中了三个中高分意图，子问题 C 只有一个 0.61 的意图。
3. 如果你粗暴地按全局分数从高到低截前 3，可能 A 拿两个、B 拿一个、C 一个都拿不到。
4. 从打分视角看这似乎合理，但从用户问题视角看就不合理了，因为用户明明问了 C 这个子问题，系统却像没看见一样。
5. 所以这一步不能只看分数，还必须看“每个子问题有没有代表”。

这就是这套算法的核心取舍：**多样性优先于纯分数最优。**

### 5. 这套封顶算法的思路是什么

1. 先统计这次所有子问题一共命中了多少意图。
2. 如果总数没有超过上限，直接返回，不做额外裁剪。
3. 如果超限，就把所有候选先拍平，放到同一个列表里按分数降序排序。
4. 然后先给每个子问题保底选一个最高分意图。
5. 最后如果还有剩余配额，再让所有剩余候选按分数竞争这些名额。

所以它不是一上来就“大家抢 3 个坑位”，而是：

1. 先保证每个子问题至少有一个发言席位。
2. 再让高分候选竞争剩余席位。

### 6. 中间为什么要引入 `IntentCandidate`

1. 原始结构是 `List<SubQuestionIntent>`，它天然按子问题分组。
2. 但全局封顶时，需要把不同子问题里的候选放到同一个分数面板里比较。
3. 这时候直接只保留 `NodeScore` 不够，因为一旦拍平后，你会丢掉“这个意图原来属于哪个子问题”。
4. 所以系统引入了 `IntentCandidate` 这个中间结构，把两件事绑在一起：`subQuestionIndex + nodeScore`。
5. 这样后面既能全局排序，也能再按子问题索引重建回原来的结构。

换句话说，`IntentCandidate` 不是为了业务语义，而是为了让“全局排序”和“按子问题回填”这两件事能同时成立。

### 7. 五步算法具体是怎么跑的

#### 第一步：统计总数

1. 先把所有 `SubQuestionIntent` 里的 `nodeScores` 数量加起来。
2. 如果总数 `<= MAX_INTENT_COUNT`，就直接返回原结果。
3. 只有真的超限，才进入后面的裁剪逻辑。

#### 第二步：收集并排序所有候选

1. 把每个子问题里的每个 `NodeScore` 都包装成 `IntentCandidate`。
2. 每个候选都会记住自己属于哪个子问题。
3. 然后把这些候选统一按分数从高到低排序。

#### 第三步：先做多样性保底

1. 依次扫描全局排序后的候选列表。
2. 对于每个子问题，先挑出它遇到的第一个候选，也就是它的最高分意图。
3. 直到每个子问题都至少拿到一个保底意图，或者候选列表扫完为止。

这一步的意义非常关键：

1. 它保证系统不会因为某个子问题分数略低，就把这个子问题整体忽略掉。
2. 用户问了几个独立问题，系统就尽量让每个问题都有一个代表。

#### 第四步：剩余配额再按分数竞争

1. 先算出保底之后还剩多少名额。
2. 如果剩余名额小于等于 0，说明配额已经被保底意图占满，后面直接结束。
3. 如果还有名额，就从剩余候选里按分数继续往下选。
4. 这时候才真正体现“高分优先”的原则。

所以这套算法不是不要分数，而是把分数优先级放在“多样性保底”之后。

#### 第五步：按子问题重建结果

1. 前面为了方便比较，候选都被拍平成全局列表了。
2. 但下游消费的还是 `List<SubQuestionIntent>` 这种结构。
3. 所以最后还要把选中的 `IntentCandidate` 再按 `subQuestionIndex` 分组，重建成新的 `SubQuestionIntent` 列表。
4. 如果某个子问题最终没有任何保留下来的意图，也会给它重建出一个空列表，而不是把这个子问题位置丢掉。

### 8. 用“3 个子问题、8 个意图”走一遍就明白了

1. 假设子问题 A 命中 2 个意图，子问题 B 命中 3 个意图，子问题 C 命中 3 个意图，总共 8 个。
2. 系统总上限是 3。
3. 那保底阶段一跑，A、B、C 会各先拿到自己分数最高的 1 个。
4. 这时候 3 个名额已经全部用完，后面就没有剩余配额了。
5. 最终结果就是 8 个意图被压成 3 个，而且恰好每个子问题各保留 1 个最高分代表。

这个例子能看出算法的真实偏好：

1. 它优先保证“每个子问题都被照顾到”。
2. 而不是追求“从全局角度看得分最高的 3 个意图”。

### 9. 为什么总量上限默认也是 3

1. 单个子问题最多 3 个、全局总数也最多 3 个，看起来用了同一个数字，但含义不一样。
2. 单题里的 3，解决的是“某个子问题别带太多候选”。
3. 全局里的 3，解决的是“这次请求总共别往下游压太多检索目标”。
4. 这个数字不是数学定理，而是工程平衡点。
5. 太少，复合问题只能回答一部分；太多，下游检索和 Prompt 上下文就会被稀释。

背后的工程考虑主要有三个：

1. 检索延迟会累加。每多一个 KB 意图，通常就多一次定向检索；每多一个 MCP 意图，通常就多一次工具调用。
2. 生成上下文会变胖。意图越多，带回来的 chunk 和工具结果越多，最后 Prompt 更长。
3. 噪音和幻觉风险会上升。不够聚焦的检索结果越多，模型后面越容易被带偏。

### 10. 这一步和下游链路怎么衔接

1. `capTotalIntents(...)` 做完后，返回的仍然是 `List<SubQuestionIntent>`。
2. 后面 `mergeIntentGroup(...)` 会再把保留下来的意图按 `KB` 和 `MCP` 拆开。
3. `KB` 意图继续去做定向知识库检索。
4. `MCP` 意图继续去做工具调用。
5. 如果某个子问题最后只剩一个 `SYSTEM` 意图，还有机会继续走系统直答短路。

也就是说，这一步不是最终决策终点，而是下游检索和调用之前的最后一道“总量闸门”。

### 11. 参数没有放之四海而皆准

1. 当前项目里常见的默认值是 `INTENT_MIN_SCORE = 0.35`、`MAX_INTENT_COUNT = 3`。
2. 这里的 `INTENT_MIN_SCORE = 0.35` 是分类阶段的保留门槛，不是第九章里检索通道的 `minIntentScore = 0.4`；前者管“单题意图要不要留下”，后者管“定向检索要不要启用”。
3. 这套数字在当前 Ragent 场景下是一个权衡结果，但换业务就未必合适。
4. 如果你的场景意图高度集中，比如法务问答，可能总量上限 1 到 2 就够了。
5. 如果你的场景天然多并发症状、多交叉问题，比如医疗分诊，3 可能又偏小。
6. 所以这些参数不是“标准答案”，而是要结合真实日志、bad case 和业务效果不断校准的。

### 12. 一句话总结

这一章的主线就是先让单个子问题做分数过滤和数量收敛，再用全局封顶算法保证多个子问题叠加后既不爆量，也不会把某个子问题饿死。

## 十一、用户问退货政策，3C、家电和服装都举手了

### 1. 为什么做完意图识别和封顶，还会剩下一个问题

1. 前面几章已经把两件事讲清楚了：单个子问题怎么打分，多个子问题怎么做总量封顶。
2. 但即使走完这两层，系统仍然可能遇到一种棘手情况：意图不是太多，而是太像。
3. 比如用户只问“退货政策是什么”，这句话本身没有指明是 3C、家电还是服装。
4. 如果这几个品类下都存在“退货政策”相关节点，而且分数也很接近，系统就很难自信地只选其中一个。
5. 这时候最危险的不是“没答案”，而是“选错方向以后答得特别像真的”。

所以第十章解决的不是“如何再多保留几个意图”，而是：**当多个候选方向都像，但系统没有把握时，要不要先反问用户。**

![第十章-歧义引导示意图](D:/develop/知识星球学习/ragent总结图/第十章-歧义引导示意图.png)

### 2. 歧义引导不是所有场景都会触发

1. 它不是意图识别后的固定步骤，而是一个按条件触发的短路分支。
2. 只有当系统发现当前问题命中了多个相近方向，且这些方向之间的分数差距不足以支撑“直接选一个”时，才会考虑引导。
3. 如果最高分明显领先，系统就应该直接往后走，不要多问一句。
4. 如果用户问题里已经明确写了品类、系统名或类别名，系统也应该直接跳过引导。
5. 所以它本质上是一道“要不要先问清楚”的判断闸门。

### 3. 为什么这个问题在电商、多系统场景特别明显

1. 意图树一旦扩展到多个品类或多个系统，类似主题就会自然地在不同分支里重复出现。
2. 电商里常见的是：3C 数码、家电、服装都各自有退货政策、保修规则、配送时效。
3. 企业知识库里常见的是：OA、保险、财务系统都各自有数据安全、权限管理、审批流程。
4. 这些节点从主题词上看非常像，但真实答案往往完全不同。
5. 所以只做“主题相关性打分”还不够，系统还要判断：这是不是一个应该先澄清范围的问题。

### 4. 触发引导前，系统先按品类做归并

1. 歧义引导不是直接拿一堆叶子节点问用户“你选哪个”。
2. 那样太细，用户体验会很差。
3. 系统会先把候选节点按更高一层的类别做归并，取每个类别里分数最强的代表。
4. 在电商场景下，这一层通常是 `CATEGORY`，也就是品类粒度，而不是最粗的 `DOMAIN`，也不是最细的 `TOPIC`。
5. 这样最后拿来比较的，就不是“3C-退货政策”“3C-退款时效”“3C-换货规则”这些细节点，而是“3C 数码”这个更适合用户选择的类别代表。

### 5. 为什么要停在 `CATEGORY`，而不是继续往上或往下

1. 如果停在 `DOMAIN`，粒度会太粗。
2. 比如电商里这几个节点可能都属于同一个 `商品服务` 大域，拿这个去问用户根本没意义。
3. 如果停在 `TOPIC`，粒度又太细，用户会看到很多几乎重复的选项，反而更难选。
4. 停在 `CATEGORY` 刚好合适：它比领域更具体，又比叶子节点更适合做人类交互。
5. 所以系统会从叶子节点往上回溯父节点，在 `CATEGORY` 级停下，把这里当作“引导粒度”。

### 6. 第一层快速判断：`shouldSkipGuidance`

1. 真正进入复杂歧义判定前，系统会先跑一个快速跳过逻辑。
2. 这一步的目标是：明显不需要引导的情况，尽早放行，不要再走后面的复杂判断。
3. 快速跳过主要看两类信号。
4. 第一类是分数差距：如果第一名和第二名差得已经很明显，就不用问。
5. 第二类是用户显式线索：如果问题里已经写了品类名、系统名或类别关键词，也不用问。

比如：

1. 用户问“3C 数码的退货政策”，虽然候选列表里可能还有家电和服装，但问题里已经明确出现了“3C 数码”，系统应该直接跳过引导。
2. 用户问“手机退货规则”，即使分类分数没有彻底拉开，后面的 LLM 二次判断通常也能看出这是 3C 方向。

### 7. 真正的歧义判定，靠的是分数比值而不是绝对分

1. 系统不会只看“第一名多少分、第二名多少分”，而是看它们的比值 `ratio = second / top`。
2. 因为绝对分在不同问题、不同知识域下波动比较大，但相对接近程度更能体现“像不像在打架”。
3. 如果第二名几乎追平第一名，就说明系统没有明显信心。
4. 如果第二名被第一名甩开很远，就说明最高分方向已经足够明确。
5. 所以歧义引导的本质不是“分数高不高”，而是“前两名接近不接近”。

### 8. 三区间判定：明确歧义、灰色地带、明确不歧义

1. 当前实现不是简单一个阈值拍脑袋决定，而是分成三个区间。
2. 如果 `ratio >= threshold`，说明前两名太接近，直接判为明确歧义，触发引导。
3. 如果 `ratio < threshold - margin`，说明第一名优势足够明显，直接判为不歧义。
4. 中间这一段灰色地带，才交给 LLM 做二次确认。
5. 这样做的目标，是把“明显的事情”交给规则，把“边界不清的事情”交给模型。

这张图对应的就是这套判定流程：

![第十章-歧义引导判定流程](D:/develop/知识星球学习/ragent总结图/第十章-歧义引导判定流程.png)

### 9. 为什么还要专门设一个灰色地带

1. 因为纯规则方案有天然两难。
2. 阈值设高了，很多其实应该引导的边界场景会漏掉。
3. 阈值设低了，很多本来已经足够明确的问题又会被系统多问一句。
4. 灰色地带的作用，就是把这部分“规则也没十足把握”的情况单独拎出来。
5. 这样系统既能保留规则判断的高效率，又能借助 LLM 的语义理解能力去补边界。

### 10. 灰色地带里的二次确认：`AmbiguityLLMChecker`

1. 当分数比值落进灰色区间时，系统会调 `AmbiguityLLMChecker.checkAmbiguity(question, ranked)`。
2. 这一步不会再把整棵意图树丢给模型，而是只给它当前问题和少量候选类别。
3. 模型要回答的问题也很单一：这到底算不算歧义。
4. 调用参数同样偏保守，比如低温度、较低 `topP`、关闭深度思考输出。
5. 如果 LLM 判断“问题里已经有足够明确的品类线索”，就不触发引导；否则就触发。

这里有个很重要的工程取舍：

1. 这一步不是为了让模型自由发挥，而是让它只做一个窄任务：判断用户是否已经表达清楚。
2. 所以即使引入了 LLM，整个歧义检测链路仍然是“规则优先、模型补边界”的风格，而不是完全把决策权交给模型。

### 11. 如果 LLM 二次确认失败，系统怎么选

1. 这类地方系统通常更偏保守。
2. 也就是：宁可多问用户一句，也不要直接选错方向后答错。
3. 所以灰色地带里如果模型判断失败、返回异常、或者解析不了，策略通常会倾向于触发引导，而不是强行继续往后查。
4. 这和前面意图识别的降级策略一脉相承：能保守就保守，别把错误路由继续放大。
5. 对问答系统来说，多一次澄清的体验成本，往往比一本正经答错的信任成本低得多。

### 12. 引导结果不是布尔值，而是一个小决策对象

1. 系统不会简单返回一个 `true/false` 说“要不要引导”。
2. 它通常会返回一个类似 `GuidanceDecision` 的决策对象。
3. 这个对象最常见的两种状态是：`NONE` 和 `PROMPT`。
4. `NONE` 表示不引导，继续下游正常流程。
5. `PROMPT` 表示生成引导文案，并要求 Pipeline 在这里短路返回给用户。

这样做的好处是：

1. 判定逻辑和执行逻辑解耦了。
2. 上层 Pipeline 不需要知道内部到底是怎么判断出来的，只要看结果是不是 `PROMPT` 就行。

### 13. 引导文案怎么生成

1. 触发引导后，系统不会现场让 LLM 再写一段自由文本。
2. 它通常会用一个固定模板，比如 `guidance-prompt.st`，把主题名和候选类别列表渲染进去。
3. 这样出来的文案更稳定，也更方便控制格式。
4. 同时候选项数量还会做兜底裁剪，比如最多展示 6 个，避免让用户看到一长串难以选择的列表。
5. 所以引导文案本质上不是“生成”，而是“模板渲染 + 选项格式化”。

### 14. 为什么这一步能直接短路 Pipeline

1. 因为一旦系统决定先引导，就说明“现在还不适合检索，更不适合生成答案”。
2. 这时继续往下做向量检索、Reranker、生成回答，只会浪费算力和延迟。
3. 所以 Pipeline 会在 `handleGuidance(...)` 这里直接短路。
4. 它会把引导文案通过现有 SSE 通道推给前端，然后 `onComplete()` 结束本轮请求。
5. 后面的系统直答、检索、RAG 生成都会被跳过。

这一步短路省掉的，其实是后面最重的那几段：

1. 定向检索
2. 重排序
3. 最终 LLM 生成

### 15. 用户选完之后，为什么下一轮通常就不会再引导

1. 因为用户的选择会进入会话记忆，成为下一轮的历史上下文。
2. 下一轮如果用户只回复“3C 数码”或者“1”，查询改写会结合上一轮引导文案，把它补全成更明确的问题。
3. 比如把“1”改写成“3C 数码的退货政策”。
4. 一旦问题里已经明确带上品类名，前面的快速跳过逻辑就会直接放行。
5. 所以这其实是一个完整闭环：引导负责问清楚，记忆和改写负责把用户选择重新拼回问题里，避免重复引导。

### 16. 一句话总结

这一章的主线就是把前两名过近的候选先拉进歧义判定，再通过比值分区、LLM 二次确认和模板引导，决定到底继续查还是先问用户。

## 十二、把前面三章和后面四段串起来看

前三章其实已经把整条链路的前半段讲清楚了：记忆负责给上下文，改写负责把用户说的话变成更适合搜索的表达，意图识别和歧义引导则负责把这句问题压到一个“能不能继续跑”的状态。也就是说，到第三章结束时，系统已经不是在判断“怎么答”，而是在判断“这条路到底该不该继续往下走”。

如果歧义引导没有触发，后面就会自然接上第四章的四个阶段：先判断是不是纯系统问题，能直答就直接答；如果不能直答，就进入多通道检索，把 KB 和 MCP 的证据分别找出来；如果检索没有结果，就立刻兜底收口；只有证据齐了，才进入 Prompt 组装与流式生成。这样前后连起来看，整套系统其实一直遵守同一个原则：该问清楚的时候先问清楚，该直答的时候直接答，该检索的时候认真检索，没依据的时候不硬编。

---

## 十三、阶段五：系统直答完整链路

系统直答这一章讲的不是普通闲聊，而是“当问题根本不需要查资料时，系统如何识别出来并直接给出回答”。这条链路的价值在于，它把明显不属于知识库和工具调用的问题提前分离出去，避免把一件本来很简单的事做得很重。

### 1. 先判断是不是纯系统问题

系统直答的入口是 `StreamChatPipeline.handleSystemOnly(ctx)`。它不会一上来就猜，而是先调用 `intentResolver.isSystemOnly(...)`，检查当前子问题的意图结果是不是只剩一个 `SYSTEM` 节点。这个判断非常严格：只要还混着 KB 或 MCP 意图，就说明这个问题还没有到“直接答就行”的程度，必须继续往后走。

这里需要特别注意，`SYSTEM` only 和“没检索到知识库结果”不是一回事。前者是路径选择问题，意味着这轮本来就不该检索；后者是检索失败，意味着系统虽然查了，但没找到证据。两者在流程上处在完全不同的位置。

### 2. 系统模板怎么选

如果确认是纯系统问题，接下来不是直接让模型自由发挥，而是先决定用哪个系统 prompt。最优先的来源是当前 `SYSTEM` 节点自己的 `promptTemplate`，因为不同系统节点可能有不同的回答风格和角色设定；如果节点没有配置模板，就回退到默认的 `answer-chat-system.st`。这就是“节点自定义优先，通用模板兜底”的策略。

`promptTemplateLoader.load(...)` 在这里的作用很直接：把模板从资源目录里加载出来，保证系统直答不依赖临时拼接的字符串，而是始终走一份稳定的模板定义。

### 3. `streamSystemResponse(...)` 怎么组消息

系统直答真正发给模型时，消息顺序也很固定：先放 system prompt，再放历史消息，最后放当前问题。`streamSystemResponse(...)` 的职责就是把这三部分拼成一个完整的 `ChatRequest`，然后交给 `llmService.streamChat(...)`。它不会插入知识库证据，也不会插入 MCP 结果，因为这一类问题本来就不需要外部检索支撑。

这条链路里，调用参数也更偏通用对话而不是知识问答检索。比如它会关掉 `thinking`，避免模型走太长的推理输出；温度也会维持在适合通用问答的水平，让回答更自然但不至于发散过度。

### 4. 为什么它必须短路

系统直答之所以必须短路，是因为这类问题再往后走检索链路，收益很小但成本很高。闲聊、打招呼、系统能力说明这些问题，本质上不需要去碰知识库或工具调用；如果硬把它们送去检索，不仅浪费时间，还会把本来很清晰的问题绕复杂。所以系统直答不是“偷懒跳过一步”，而是“把问题放回最合适的路径上”。

### 5. 一句话总结

这一章的主线就是用最短路径把纯系统问题从重链路里摘出来：先判断是不是 SYSTEM only，再选模板、拼消息、流式输出。

## 十四、阶段六：多通道检索完整链路

多通道检索这一章讲的是：系统怎么把“找资料”这件事拆成多个来源、多个通道、多个后处理步骤，再把结果统一收口成可供回答使用的证据上下文。它不是单纯的“搜一搜”，而是一条完整的检索编排链路。

### 1. 检索入口为什么只有一个

整个检索链路的入口只有 `RetrievalEngine.retrieve(...)`。这个方法拿到的不是原始问题，而是已经经过意图识别和封顶后的 `subIntents`，所以它不会再去猜用户到底想问什么，而是直接根据意图分流执行。这个设计的好处是，把“理解问题”留给前面的链路，把“执行检索”留给这里，职责分得很清楚。

### 2. `RetrievalEngine` 怎么拆开 KB 和 MCP

`RetrievalEngine` 先把每个子问题包装成 `SubQuestionContext`。在这个过程中，它会用 `NodeScoreFilters.kb(...)` 和 `NodeScoreFilters.mcp(...)` 把当前意图里的 KB 节点和 MCP 节点分别筛出来。KB 路径交给 `retrieveAndRerank(...)`，MCP 路径交给 `executeMcpAndMerge(...)`，最后再把这两条链路的结果统一合并成一个 `RetrievalContext`。

### 3. KB 检索为什么要分定向和全局

KB 检索不是一把梭，而是两条通道并行：`IntentDirectedSearchChannel` 负责定向召回，`VectorGlobalSearchChannel` 负责补底。定向通道的核心是“只在明确知道该搜哪个 collection 时才搜”，所以它会先筛掉低分意图，再按 `collectionName` 去对应知识库精确检索；而全局通道更像安全网，当系统对意图没有那么自信时，它会把所有 KB collection 都扫一遍，避免“方向选错了连目标库都没进去”。

两个通道跑完之后，还会进入 `MultiChannelRetrievalEngine` 的后处理链。`DeduplicationPostProcessor` 会根据通道优先级和 chunk 唯一标识做去重，优先保留更可靠通道的结果；`RerankPostProcessor` 则会把所有候选片段交给重排模型再排一次，最后只留下最值得进入 Prompt 的 Top-K。

### 4. 通道内部为什么还要再并行

1. `SearchChannel` 解决的是“先跑哪个通道”，但一个通道内部往往还要再查多个 Collection。
2. 这里用的是 `AbstractParallelRetriever` 的模板方法模式：父类把并行提交、等待、收集、容错和统计封成 `final` 骨架，子类只实现任务创建、目标标识和统计名。
3. `IntentParallelRetriever` 负责多个意图节点的并行检索，会先根据 `NodeScore` 预计算每个意图自己的 `topK`；`CollectionParallelRetriever` 只接收 `String` 形式的 Collection 名称，逻辑更轻。
4. 更外一层的子问题并行用 `ragContextExecutor`，通道并行用 `ragRetrievalExecutor`，内层 Collection 并行用 `ragInnerRetrievalExecutor`；三个线程池彼此隔离，避免嵌套并行时抢资源。
5. `TTL` 再把父线程的 ThreadLocal 上下文带进子线程，链路追踪不会断。
6. 这张图对应的就是“子问题级 + 通道级 + Collection 级”三层并行编排：

### 5. 为什么 30 条结果最后只给模型 5 条

1. 检索阶段返回多，问题不是“少不够”，而是“多了重复、分数不统一、噪音大”。
2. `SearchResultPostProcessor` 统一定义了后处理接口，`process(chunks, results)` 同时接收流水线里的 Chunk 列表和原始通道结果，方便不同处理器使用不同输入。
3. `executePostProcessors()` 会按 `getOrder()` 把处理器串起来，`DeduplicationPostProcessor` 先跑，`RerankPostProcessor` 后跑，顺序不能反。
4. 去重时会按通道优先级处理：`INTENT_DIRECTED -> 1`、`KEYWORD_ES -> 2`、`VECTOR_GLOBAL -> 3`，同一条 Chunk 重复命中时优先保留更可靠的来源。
5. 精排时 `RerankPostProcessor` 把候选交给 Cross-Encoder，统一成可比的 `relevance_score`，然后再截断到最终 topK。
6. 所以链路大致是 30 条原始结果，先去重到 20 条左右，再精排并截断到 5 条给模型。
7. 如果 Rerank 模块挂了，`NoopRerankClient` 会兜底，让系统至少还能按原始顺序把结果收口，不至于整条链路炸掉。
8. 这张图对应的就是后处理器链和结果漏斗：

### 6. MCP 检索为什么要先抽参数

MCP 这条链路不是查知识库，而是调工具。`executeMcpAndMerge(...)` 会先把 `NodeScoreFilters.mcp(...)` 过滤出来的工具意图拿到，再通过 `LLMMCPParameterExtractor` 从用户问题里抽取参数。`buildMcpRequest(...)` 会把 toolId、问题和参数封装成标准的 `MCPRequest`，`executeSingleMcpTool(...)` 负责找到对应执行器并真正调用工具。工具返回后，再由 `DefaultContextFormatter.formatMcpContext(...)` 把多个响应整理成一份适合 Prompt 复用的动态数据。

这条链路里，参数抽取很关键，因为 MCP 调用不是“把问题原样丢出去”，而是要先把用户自然语言转换成工具能理解的结构化参数。没有这一步，很多工具即使被找到也没法正确执行。

![第十四章-MCP 工具调用主线](D:/develop/知识星球学习/ragent总结图/iShot_2026-04-23_16.38.71.png)

### 7. 知识库答不了的问题，为什么要交给 MCP

1. KB 和 MCP 在系统里不是二选一，而是两类证据源。
2. KB 更擅长静态知识、制度说明、文档条款；MCP 更擅长实时数据、业务状态和外部动作。
3. 当问题天然更像“查表、查状态、调接口”时，继续在 KB 里硬搜只会浪费一次检索机会。
4. 所以 `RetrievalEngine` 先通过 `NodeScoreFilters.kb(...)` / `NodeScoreFilters.mcp(...)` 把两路意图拆开，再各自执行。
5. 这也是为什么 MCP 不是 KB 的替代品，而是 KB 查不到时的另一个证据面。

![第十四章-一次 MCP 工具调用链路](D:/develop/知识星球学习/ragent总结图/iShot_2026-04-23_16.38.72.png)

### 8. 为什么最后要统一成 RetrievalContext

检索链路最终输出的不是一堆散片段，而是 `RetrievalContext`。它把 `kbContext`、`mcpContext` 和 `intentChunks` 三部分放在一起，后续 Prompt 组装阶段就只需要消费这一份结构化对象，不用再回头猜这些片段分别来自哪里。也就是说，`RetrievalContext` 的作用不是简单“装结果”，而是给生成阶段提供一份已经整理好的、带来源标识的证据包。

### 9. 一句话总结

这一章的主线就是把 KB 和 MCP 两条证据链拆开，再通过并行检索、去重、重排和结果收口，把真正能回答问题的上下文交给模型。

## 十五、阶段七：空结果兜底完整链路

空结果兜底这一章讲的是：当检索已经跑完，但还是没有拿到任何能支撑回答的证据时，系统应该怎么安全收口。它的重点不是“继续找”，而是明确告诉用户“这轮没有找到可用上下文”。

### 1. 什么时候会触发兜底

兜底判断发生在 `StreamChatPipeline.handleEmptyRetrieval(ctx, retrievalCtx)`。系统先看 `retrievalCtx.isEmpty()`，如果 KB 和 MCP 两边都没有上下文，就说明这轮请求已经没有可供继续生成的证据了。这个判断非常关键，因为它把“空证据”从“可继续回答”的状态里彻底区分出来。

### 2. 兜底时具体做了什么

一旦进入兜底分支，Pipeline 就不会再往后走 Prompt 组装和流式生成，而是直接通过 SSE 把兜底信息发回前端。这样用户得到的是一个明确的结束信号，而不是一个挂起或异常的请求。它的作用不是补搜，而是把“没查到”这个事实直接暴露出来。

### 3. 为什么这里不能让模型自由发挥

如果检索已经空了，却还把这份空上下文交给模型，模型就很容易开始基于常识瞎补，最后反而答出一段看起来像真的、其实没有依据的内容。`handleEmptyRetrieval(...)` 的意义就在于把这种风险提前挡住：没有证据就不要生成，不要把“空”伪装成“可答”。

### 4. 一句话总结

这一章的主线就是在检索空掉时及时止损，直接把“没找到”的事实发给前端，避免模型拿空上下文继续生成。

---

## 十六、阶段八：Prompt 组装与流式生成完整链路

Prompt 组装与流式生成这一章讲的是：当系统已经拿到了记忆和检索证据以后，如何把这些材料整理成一个真正适合模型执行的消息序列，并把生成结果稳定地流式输出、落库、回写到会话中。

### 1. 先把意图和证据收拢成统一上下文

最终生成并不是直接从检索结果开始，而是先经过 `streamRagResponse(...)`。这个方法会调用 `intentResolver.mergeIntentGroup(...)`，把当前请求里命中的 KB 意图和 MCP 意图重新分组，然后再把它们和 `RetrievalContext`、历史记忆、当前问题一起封装成 `PromptContext`。这样做的好处是，生成阶段拿到的是一份已经整理好的上下文，而不是一堆散落的片段。

### 2. `RAGPromptService` 怎么选模板

真正组织最终提示词的是 `RAGPromptService`。它先通过 `plan(context)` 判断当前场景是 KB_ONLY、MCP_ONLY 还是 MIXED，然后分别走 `planKbOnly(...)`、`planMcpOnly(...)` 或 `planMixed(...)`。如果当前意图里只有一个节点而且节点本身带了 `promptTemplate`，它还会优先使用节点自己的模板；否则才回退到默认的场景模板，比如 `answer-chat-kb.st`、`answer-chat-mcp.st` 或 `answer-chat-mcp-kb-mixed.st`。

这层逻辑的意义很大，因为不同场景下模型面对的证据结构是完全不同的。只有 KB 时，模型更像是在基于文档回答；只有 MCP 时，模型更像是在基于动态数据回答；两者同时存在时，则必须把静态知识和动态结果一起综合起来看。

### 3. `buildStructuredMessages(...)` 的消息顺序为什么这么定

`buildStructuredMessages(...)` 负责把最终消息真正排好顺序。它先放 system prompt，再把 MCP 证据作为 system 消息放进去，把 KB 证据作为 user 消息放进去，然后追加历史消息，最后才放当前问题。这个顺序不是随便定的，而是为了让模型先看到规则，再看到证据，再看到上下文，最后聚焦当前问题。

如果是多子问题场景，这里还会把子问题显式编号后再交给模型。这样模型就不会把几个问题混着答，也更容易做到“每个子问题都被回答到”。这一点在多轮、多问题场景里尤其重要。

### 4. 流式输出和记忆回写怎么配合

最终消息准备好后，系统通过 `llmService.streamChat(...)` 开始流式输出。输出过程中，`StreamChatEventHandler` 会一边把增量内容切片发给前端，一边在内存里拼接完整答案。等到 `onComplete()`，它会把完整回答连同思考内容写回会话记忆；如果这轮还是新对话，它还会顺手补一个标题，方便后续会话列表展示。

所以这里不是简单“把答案发出去”，而是把“生成、展示、落库”三件事串成了同一条流式闭环。

### 5. promptTemplate 和 promptSnippet 不是一回事

1. `promptTemplate` 更像整页 system prompt 的主模板，单意图时可以直接替换整个场景模板。
2. `promptSnippet` 更像局部补丁，只注入到 `<rules>` 之类的固定位置。
3. 主模板决定大框架，片段只补规则和个别节点说明，这样才不会把场景逻辑写散。
4. 多意图场景里，`promptSnippet` 还能把不同节点的补充规则合并进同一份上下文。

### 6. KB 上下文为什么放 user 而不放 system

1. `system` 负责角色、规则和边界，`user` 更适合承载可引用证据。
2. KB 文档本质上是“要被模型读到的材料”，放到 `user` 里可以避免和系统规则混淆。
3. 这样还能降低 `Lost in the Middle` 风险，让证据更贴近问题结尾。
4. 代码里就是把 `<documents>` 放进 user 消息，而不是写进 system。

### 7. Temperature 为什么分档

1. KB_ONLY 用 `0.0`，重点是忠实转述。
2. MCP 场景用 `0.3`，允许把结构化数据转成自然语言。
3. SYSTEM 闲聊用 `0.7`，留一点表达弹性。
4. 这样调温度不是风格偏好，而是按场景降低幻觉和发散。

### 8. 一个 MIXED 场景的拼装样例

1. `buildStructuredMessages(...)` 先把 system prompt、history、MCP 证据、KB 证据和当前问题按固定顺序排好。
2. 如果当前既有 KB 又有 MCP，它会走 `MIXED` 场景模板，把静态知识和动态数据同时交给模型。
3. 这时 `temperature=0.3`、`topP=0.8`，目标是让模型把证据拼起来，而不是自由发散。
4. 最终构建出来的还是一份标准 `ChatRequest`，下游只认 `messages`、`temperature`、`topP` 这些调用参数。

### 9. 一句话总结

这一章的主线就是把记忆和检索证据整理成稳定的 Prompt，再通过流式输出把答案送回前端，并顺手把回答写回记忆，供下一轮继续用。

## 十七、答案是怎么一个字一个字蹦出来的：流式生成完整链路

这一章讲的是从 `GET /rag/v3/chat` 到前端看到逐字输出，中间到底经过了哪些层。它的核心不是“LLM 会流式吐 token”这么简单，而是 Controller、Service、Pipeline、模型客户端和事件处理器五层一起把流接起来。

![第十七章-流式生成完整数据流](D:/develop/知识星球学习/ragent总结图/image-20260504123359600.png)

### 1. 五层各自负责什么

1. `RAGChatController` 创建 `SseEmitter`，把 HTTP 请求变成 SSE 连接。
2. `RAGChatServiceImpl` 生成 conversationId 和 taskId，组装 `StreamChatContext`，再启动 pipeline。
3. `StreamChatPipeline` 负责记忆加载、改写、意图识别、检索、Prompt 组装和流式调用。
4. `RoutingLLMService` 和 `OpenAIStyleChatClient` 负责首包探测、模型选择、SSE 解析和 token 传输。
5. `StreamChatEventHandler` 负责把 `onThinking`、`onContent`、`onComplete`、`onError` 转成前端能懂的 SSE 事件。

### 2. `StreamCallback` 为什么只保留四个核心回调

1. `onThinking(String)` 负责思考内容，和正文分开推送。
2. `onContent(String)` 负责正文 token，一边读一边推。
3. `onComplete()` 负责收尾、落库和关闭连接。
4. `onError(Throwable)` 负责通知前端并释放资源。
5. 这四个回调把“读流、转发、收尾”三件事切得很清楚。

### 3. 为什么要分块推送

1. `sendChunked()` 按指定字符数切块推 SSE，避免一次事件太大。
2. 它用 `codePointAt()` 处理多字节 Unicode，emoji 这类字符不会被拆坏。
3. SSE 事件一般分成 `META`、`MESSAGE`、`FINISH`、`DONE` 四类，前后端靠事件类型约定协议。
4. 这样做的结果是，前端不等完整答案结束也能看到增量内容。

### 4. 取消句柄为什么要后绑

1. 回调对象在 Service 层就创建了，但 `streamChat()` 还没返回句柄。
2. 取消句柄只有在模型真正开始调用后才存在，所以要等 `streamChat()` 返回再 `bindHandle()`。
3. 如果用户在句柄绑定前就点了停止，绑定动作会检测到已取消状态并立即中断。
4. 这一步把“句柄还没来得及绑定”的竞态也兜住了。

### 5. 一句话总结

流式生成的本质，是把“模型吐 token”这件事拆成 HTTP 建连、Pipeline 编排、模型读流、事件转发、前端增量渲染五段接力，让答案一边生成一边到达用户。

## 十八、用户点了停止生成后，集群里发生了什么

这一章讲的是取消链路：前端点停止之后，后端怎么把“停”的信号穿过集群、穿过回调、再把已经生成的内容妥善收口。

![第十八章-停止生成主图](D:/develop/知识星球学习/ragent总结图/image-20260504182747183.png)

![第十八章-任务生命周期](D:/develop/知识星球学习/ragent总结图/iShot_2026-04-23_16.38.73.png)

### 1. 前端只做两件事

1. 先 `POST /rag/v3/stop?taskId=xxx`。
2. 等后端回 `cancel` 事件后再关 `EventSource`。
3. 前端不直接断开连接，而是先走停单，再等后端确认，这样已生成内容才有机会回传。

### 2. `StreamTaskManager` 为什么要同时用 Guava Cache 和 Redis

1. Guava Cache 提供本机快速查找。
2. Redis 提供跨节点可见性和 30 分钟 TTL。
3. `cancel()` 先写 Redis 再 publish，避免只通知到一半节点。
4. `subscribe()` 在容器启动时监听取消频道，收到后在本机执行 `cancelLocal()`。

### 3. `StreamTaskInfo` 的生命周期

1. 先创建 task entry。
2. `register(sender, supplier)` 绑定 sender 和 cancel supplier。
3. 如果 Redis 已标记取消，立刻推 `CANCEL + DONE` 并 close。
4. `bindHandle(taskId, handle)` 发现已取消就立刻 `handle.cancel()`。
5. 正常流式时 `onContent()` 和 `onThinking()` 每次都要检查 `isCancelled()`。

### 4. 怎么真正停掉正在跑的 LLM 流

1. `cancelLocal()` 先用 CAS 把 `cancelled` 置 true。
2. `OkHttpCancellationHandle.cancel()` 再中断底层 HTTP stream。
3. 回调里先保存已生成内容，再推 `CANCEL` 和 `DONE`。
4. `onComplete()` 和 `cancelLocal()` 都走幂等关闭逻辑，避免重复 close。
5. 这条链路的目标不是“粗暴断流”，而是“停得住，也收得回”。

### 5. 一句话总结

停止生成不是前端一个按钮这么简单，而是一个跨节点、跨线程、跨回调的幂等取消协议，既要立刻停掉 LLM 流，也要把已经生成的内容安全落回会话。

## 十九、10 个人同时提问，为什么只有 3 个坑位

这一章讲的是并发控制。它解决的问题不是“每秒来了多少请求”，而是“同时有多少个长请求真的在占资源”。对于 SSE + RAG 这种长耗时链路，表面 QPS 看起来不高，实际并发却可能把 GPU、连接和线程池一起打满。

![第十九章-QPS 并发占用误区](D:/develop/知识星球学习/ragent总结图/iShot_2026-04-23_16.38.74.png)

![第十九章-排队限流全链路](D:/develop/知识星球学习/ragent总结图/iShot_2026-04-23_16.38.75.png)

### 1. 为什么不能简单加一个 QPS 限流

1. 长请求下，QPS 相同但并发差很多。
2. `Semaphore` 只管本机，集群会把并发乘起来。
3. 体验上，直接拒绝比排队更糟，尤其对 SSE/RAG。

### 2. 为什么是分布式公平排队

1. `FairDistributedRateLimiter` 负责通用公平闸门。
2. `ChatQueueLimiter` 负责 SSE 特有的排队、等待和回调。
3. `RPermitExpirableSemaphore` 负责集群总坑位，`RBucket` 负责 entry TTL，`ZSET` 负责 FIFO，`RAtomicLong` 负责 seq，`RTopic` 负责广播。

### 3. `enqueue()` 怎么同时入队和立即抢占

![1a30b3e9-3929-408b-ae8a-3b7eec20629b](D:\develop\知识星球学习\ragent总结图\1a30b3e9-3929-408b-ae8a-3b7eec20629b.png)

1. 先创建 `Ticket`，绑定 `cancelBinder` 和 `onAcquire`。
2. 再拿 `seq` 入 `ZSET`，保证 FIFO 顺序稳定。
3. 然后立刻走 `tryAcquireIfReady()` 的四步检查：看 ticket、看 `availablePermits()`、走 Lua 原子出队、发放 `permitId`。
4. 抢到就进入专用线程池执行业务，没抢到就继续留在队列里等下一轮唤醒。

### 4. 为什么不能用朴素的 List + Semaphore

1. `List` 不能高效做队头检查和任意删除。
2. 只靠本地 `Semaphore`，集群并发会被放大。
3. 只有 `ZSET + Lua + entry marker + Pub/Sub` 这一套，才能同时满足 FIFO、公平性和跨节点一致性。

### 5. 一句话总结

这个限流不是在管“每秒进来多少请求”，而是在管“同一时刻到底有多少个长请求真的占着坑位”，所以核心方案一定是分布式排队，而不是单机计数。

## 二十、抢不到许可时，系统是等还是拒

这一章继续顺着排队链路往下看：当请求没抢到许可时，系统不是立刻拒掉，而是会先给它一个等一等的机会。只有超过等待窗口，才会走拒绝分支。

![第二十章-等待与拒绝主图](D:/develop/知识星球学习/ragent总结图/iShot_2026-04-23_16.38.84.png)

![第二十章-轮询流程](D:/develop/知识星球学习/ragent总结图/iShot_2026-04-23_16.38.83.png)

![第二十章-跨集群唤醒](D:/develop/知识星球学习/ragent总结图/iShot_2026-04-23_16.38.80.svg)

![第二十章-防惊群](D:/develop/知识星球学习/ragent总结图/iShot_2026-04-23_16.38.81.svg)

### 1. 为什么要有等待路径

1. 对长耗时 SSE 请求来说，直接拒绝很伤体验。
2. `scheduleQueuePoll()` 给抢不到许可的请求一个 deadline 内重试机会。
3. `ChatQueueLimiter` 先把请求转成 `Ticket`，再交给轮询调度。

### 2. `scheduleQueuePoll()` 做了什么

1. `intervalMs = max(50, pollIntervalMs)`，轮询频率不会太粗。
2. 它会同时注册 scheduler 和 `PollNotifier`。
3. poller 每次触发先检查 ticket 是否还 `pending`，再看 deadline。
4. 到点了就 `timeout()`，拿到许可就 `grant(permitId)` 并触发 `onAcquired`。

### 3. 为什么需要 Pub/Sub 和轮询并存

1. `publishQueueNotify()` 负责节点间唤醒。
2. `PollNotifier` 负责防惊群、去抖和合并多次通知。
3. 只靠广播会漏掉注册时序，只靠轮询会慢。
4. 两者叠加后，节点 B 释放许可，节点 A 能在很短时间内重新抢占。

### 4. 成功、等待、拒绝三条路径

1. 成功路径：前 3 个请求抢到 permit 直接执行。
2. 等待路径：第 4 到第 10 个进入轮询，直到 deadline 或被唤醒。
3. 拒绝路径：超过 `max-wait-seconds` 后 `ticket.timeout()`，写会话记忆并向前端返回 `META + REJECT + FINISH + DONE`。
4. 这就是“等还是拒”的分界线。

### 5. 一句话总结

抢不到许可时，系统不是简单拒绝，而是先通过 deadline + 轮询 + 跨集群广播给请求一个等待窗口，等不到才正式收口。
